# Fact sheet: chapter 3, The disk

Every claim the chapter makes, one line each, with its source, in the order of the chapter. A claim without a source goes to the list at the end and stays out of the draft. A general fact about the Amiga, its disk format, its program format, the 68000 or C that the repository does not state is sourced in a reference work outside the repository, named with its chapter or section, and marked **(reference)**, so that the fact-check can weigh it; a fact about this game is always sourced in the repository. These reference works are cited:

- *The .ADF (Amiga Disk File) format FAQ*, Laurent Clévy, version 1.11 (2005), cited as ADF FAQ with its sections "Amiga floppy disk geometry" and "The logical organisation of an Amiga volume" (the root block).
- *The AmigaDOS Manual*, Commodore-Amiga, third edition (Bantam, 1991), cited as ADM with its chapter "Amiga Binary File Structure" (the hunk format: the block types, the hunk header with its sizes and memory flags, the relocation blocks).
- *Amiga ROM Kernel Reference Manual: Includes and Autodocs*, Commodore-Amiga, third edition (Addison-Wesley, 1991), cited as RKM Autodocs with the entry `dos.library/LoadSeg`.
- *Amiga ROM Kernel Reference Manual: Libraries*, Commodore-Amiga, third edition (Addison-Wesley, 1991), cited with its chapters "Introduction to Exec" (several tasks in one shared memory) and "Exec Memory Allocation" (memory of kinds, `MEMF_CHIP` or `MEMF_FAST`).
- *M68000 Family Programmer's Reference Manual*, Motorola (M68000PM/AD), cited as PRM with its sections 1 "Introduction" (data formats, two's complement, big-endian memory), 2 "Addressing Capabilities" (address register indirect with displacement, program counter relative, absolute long) and 3 and 4 (the condition tests of `Bcc`, signed and unsigned; `EXT`, `DIVS`, `MULS`, `LINK`, `UNLK`, `JSR`).
- *EA IFF 85: Standard for Interchange Format Files*, Electronic Arts (1985), cited as IFF 85 with its section on chunks, together with Electronic Arts' *ILBM: IFF Interleaved Bitmap* (1986) for the meaning of `CMAP` and `BODY` and the row compression ByteRun1.
- For C and the port's compilers: ISO/IEC 9899:2011, 6.5 paragraph 5 (an overflow of a signed integer is undefined behaviour); the WebAssembly tool conventions' *Basic C ABI* (`BasicCABI.md`, the data types), cited as wasm C ABI; Apple's *64-Bit Transition Guide* (the LP64 data model) for the native build; the *WebAssembly Core Specification*, section on memory instructions (little-endian), cited as wasm spec.

## An image of the floppy

4. The repository keeps the disk as an image, `original/wof.adf`, and its files extracted verbatim with xdftool under `original/disk/`; nothing in the project writes to either. Source: `SPEC.md` 2; `CLAUDE.md`, Rules (`original/` is read-only).
5. An ADF is a copy of an Amiga floppy block by block: a double-density disk is laid out in cylinders of two tracks, each track a row of blocks of one size, adding up to 880 KB, the size of `original/wof.adf`; exactly, 80 cylinders of two tracks of 11 blocks of 512 bytes, 1,760 blocks, 901,120 bytes, which the prose leaves to this sheet by the numbers rule. Source: ADF FAQ, "Amiga floppy disk geometry" **(reference)**; `stat -f %z original/wof.adf` gives 901,120; `python -c "print(80*2*11*512, 901120//512)"` gives 901120 1760.
6. The disk's file system is AmigaDOS's original one, which keeps the top directory in block 880, the middle of the disk. Source: `SPEC.md` 3.1 (OFS); `tools/headless_os.py` (`ROOT_BLOCK = 880`, "of a double-density disk"); ADF FAQ, "The logical organisation of an Amiga volume" **(reference)**.
7. A directory spreads its entries over 72 chains by a hash of their names, and the chains decide the order in which it lists its files, which is the order of the saved games in the load dialog (chapter 1). Source: `tools/headless_os.py` (`HASH_SIZE`, 72); `re/notes/frontend.md`, "The order of the file list"; `SPEC.md` 3.4, the dos row ("the order of the entries is behaviour"); chapter 1 (the order of the saved games in the load dialog).
8. The port and its tools read the extracted files; the image is read for that order alone, which the headless original hands the game as the machine would. Source: `SPEC.md` 5, step 2 (the blob from the files of 3.1); `re/notes/headless.md`, "Directories" (`headless_os.adf_order`); `re/notes/frontend.md` (nothing taken from `wof.adf` at build time).
9. The image confirms the chain of every file on the disk; how a real machine walks the chains, and where it puts a newly saved file, is documented behaviour that no run on a machine confirmed, as chapter 1 said; chapter 20 has the rest. Source: `re/notes/frontend.md`, "The order of the file list" (every entry of five directory blocks has the chain the hash gives, `test_the_disk_image_gives_the_order_the_file_system_hands_out`; "Unobserved"); chapter 1's prose ("neither a run nor the disk has confirmed it"); `book/BOOK.md` 3, chapter 20.
10. At start-up `s/startup-sequence` runs a small command of the disk's own, enters `Wings_of_Fury` and starts `Wings`; beside it lies a second copy of the program, `Wings2`, byte for byte the same, for no reason the disk tells. ## The little there was to decode

35. The game's own packed format, `Rpck`: the four letters, the unpacked size in four bytes, then control bytes read as signed: a negative one, −n, copies the next n bytes, any other, n, repeats the next byte n + 1 times. Source: `SPEC.md` 3.5, "`Rpck` compression wrapper"; `tools/rpck.py`, `unrle()`.
36. Ten files are packed, eight shape containers and two palettes; the game's loader unpacks any file that begins with `Rpck`. Source: `SPEC.md` 3.5; the first four bytes of every file of `shapes/`; `SPEC.md` 4, "The oracle" ("all ten packed files").
37. A shape container, `PPkc`: the number of shapes, a name of four characters for each, where each shape's entry begins, then the entries; an entry is a header of 20 bytes, with the width and height, the hotspot (the point that lands on the drawing position, which callers subtract) and, for each stored plane, the screen's bitplanes it lands in, a shape storing fewer planes than the screen may have; the planes follow. Source: `SPEC.md` 3.5, "`PPkc` shape container" (the masks, `01 02 04 18` storing four planes); `re/notes/shapes.md`, "Record header, complete" (the hotspot "callers subtract it from the draw position").
38. The game asks for its shapes by name, through lists of names in its data, looking most up once, when it loads a container, and a few as it needs them. Source: `re/notes/shapes.md`, Summary and "Names looked up at run time"; `SPEC.md` 3.5.
39. The figure `packed-selectrank`: the rank selection's shapes; `0xDA`, 218, counts as 218 − 256 = −38, so 38 bytes are copied, the container's letters, its count and its names; `0x05` writes a zero six times; `0xD2` copies 46 bytes; `0x17` writes `0xFF` 24 times, the top row of the first shape's first stored plane, 192 pixels set; the caption: `shapes/selectrank.shp`, 1,656 bytes on the disk, 5,630 unpacked. Source: the file's bytes (`xxd`); `tools/rpck.py`; `tools/ppkc.py` `parse()` (eight shapes of 192 x 9, the first with masks 1, 14, 16); `stat`; the figure, described under "Figures".
40. IFF is a file of chunks, each a name of four letters, its length and its contents; an ILBM picture's chunks give its size, its colours (`CMAP`) and its bitplanes, each row packed (`BODY`); three palette files are a bare `CMAP` chunk. Source: IFF 85, chunks, and ILBM **(reference)**; `SPEC.md` 3.5, "Pictures" and "Palettes".
41. The game reads its pictures with a reader of its own, which also knows a private chunk, `CMP2`, for a second palette and the line where it begins, though no file on the disk carries one; the port carries that reader over. Source: `SPEC.md` 3.5, "Pictures"; `re/notes/display.md`, the `CMP2` row ("split line from the chunk, colour table 2 ... No file on the disk contains the chunk").
42. The sound effects and the maps need nothing decoded; for the core the port wrote no decoders but ported the original's loaders, routine by routine; decoders in Python under `tools/` serve the tools, the tests and the book's figures. Source: `SPEC.md` 3.5 and 5, step 2 ("the core contains the ported loaders"); `re/notes/porting-m1.md`, "The routines"; `SPEC.md` 4 (`tools/rpck.py`, `tools/ppkc.py`, `tools/map_decode.py`).

## The executable, a hunk file

44. An Amiga program is a hunk file, AmigaDOS's format for programs, made of hunks, parts loaded into memory whole: a code hunk holds instructions, a data hunk variables with their starting values, a BSS hunk memory that starts at zero, given in the file by its size alone. Source: ADM, "Amiga Binary File Structure" **(reference)**; `tools/hunk.py` (the types `0x3E9`, `0x3EA`, `0x3EB`; a BSS hunk is `bytearray(n)`); `SPEC.md` 3.2.
45. The file opens with a header that gives the number of hunks and their sizes; each hunk follows with its contents, a list of places to correct and an end mark, every part opening with a number of four bytes that says what it is. Source: `tools/hunk.py` (`0x3F3`, the first and last hunk and the sizes; `0x3EC` the relocations; `0x3F2` the end); ADM **(reference)**.
46. `Wings` has one hunk of each kind: code 77,644 bytes, the instructions and the story and most other texts, each after the routine that uses it; data 20,464 bytes in memory, of which the file stores the first 15,456, the rest starting at zero; BSS 4 bytes. Source: `SPEC.md` 3.2 (`0x3C60` initialised; "String literals live in the CODE hunk, after the routine that uses them"); `tools/hunk.py original/disk/Wings_of_Fury/Wings` (`0x12f4c`, `0x4ff0`, `0x4`); the parts walked by a script (the data part stores `0x3C60` bytes); `re/tables.toml` (21 of the 36 string entries read the code hunk; claim 91).
47. A relocation names a place in a hunk that holds an address, written as an offset from the start of its target hunk; the loader corrects it by where the target hunk landed; the code hunk has 22 relocations, the data hunk 247. Source: `tools/hunk.py` (`v + segs[target]['base']`; the counts 5 + 17 and 34 + 213); ADM **(reference)**.
48. AmigaDOS loads a program with `LoadSeg`, which reads a hunk file, puts each hunk wherever it finds free memory of the kind the file asks for and applies the relocations; the game loads its music with it, and the system loaded `Wings` the same way. Source: RKM Autodocs, `dos.library/LoadSeg` **(reference)**; ADM **(reference)**; `SPEC.md` 3.4, the `LoadSeg` row; `re/notes/music.md`, "The two files".
49. `wofsongs` asks for chip memory, where Paula can reach its sound samples. Source: `SPEC.md` 3.1 ("one chip-memory hunk"); the header read by a script (bit 30 set in the data hunk's size word); ADM, the memory flags **(reference)**.
50. Symbols are the names a program file may keep for its routines and variables; `Wings` keeps none, no name surviving in it as a symbol (one survives as data, the sound interrupt's node name, which the prose leaves out); every name in the book's listings was given by the project, chapter 4; the music player kept its symbols, twenty in its code. Source: `tools/hunk.py` output (`syms= 0` for the three hunks of `Wings`; 20 for `songplay`'s code); `re/Wings.lst` `0x026204` (`"SoundFX_IntHandler"`, data); `SPEC.md` 4, "Naming workflow" (`re/names.txt`); `book/BOOK.md` 3, chapter 4.
51. The figure `hunks`. Source: the figure, described under "Figures".

## One layout for every address

52. On a real Amiga, `LoadSeg` chooses the addresses anew at every start, so an address written into a note would mean nothing the next day. Source: claim 48; claim 26 (a saved game's addresses of its machine).
53. The fixed load layout: the code at `0x010000`, the data at `0x023000`, the BSS at `0x028000`, each hunk at the next 4 KB boundary after the one before; every address in the specification, the listing and the oracle uses it. Source: `SPEC.md` 3.2; `tools/hunk.py`, the `bases` loop (`(a + len + 0xFFF) & ~0xFFF`); `CLAUDE.md`, Rules.
54. The disassembler that writes the listing (the program written out as assembly language, chapter 4's term), the oracle, the headless original and the build's extractor of tables all load the program that way. Source: `SPEC.md` 4 (`tools/hunk.py`, "hunk loader used by all of the above"); `re/notes/headless.md`, "Memory map"; `tools/extract_tables.py`, `Image`; the glossary's entry Listing.
55. `0x01C982` is `record_at` in the listing, in the notes, under the oracle and in its port's comment. Source: `re/names.txt` (`01c982 record_at`); `re/notes/porting-m4.md` to `porting-m7.md` (named there); `tests/test_oracle_m4.py`; `src/player.c` (`orig 0x01C982`).
56. The running port holds no such addresses: where the original keeps a pointer, the port keeps an offset or an index. Source: `SPEC.md` 7.2 ("a pointer into the map a byte offset"; "Save states and test comparisons must not depend on host pointer values").

## Manx Aztec C

57. The game's C was compiled with Manx Aztec C. Source: `SPEC.md` 3.2.
58. (Replaced by claim 100, the owner's correction of the layout.)
59. A4 is the small-data base, holding an address inside the data, from which every variable is reached by an offset of 16 bits. Source: `SPEC.md` 3.2; `tools/disasm.py` docstring.
60. The program's first instruction (`0x010000`) jumps to the C library's start-up code, `c_startup` (`0x021F2E`), which first calls `geta4` (`0x021FA0`), two instructions, `lea $2affe.l,a4` and `rts`; the file holds `0x7FFE` there with a relocation into the data hunk, so A4 is the data's address plus 32,766 wherever the data lands: `0x02AFFE` in the fixed layout. Source: `re/Wings.lst`, `0x010000`, `0x021F2E`, `0x021FA0`–`0x021FA6`; the bytes in the file (`49f9 00007ffe`); `tools/hunk.py`, the code hunk's relocation into the data at `0x021FA2`.
61. An offset of 16 bits reaches 32 KB either way, which from A4 takes in the whole data hunk from its first byte; exactly, from 32,768 bytes below the register to 32,767 above it, from `0x02AFFE` that is `0x022FFE` to `0x032FFD`, which the prose leaves to the hunks figure. Source: PRM 2, address register indirect with displacement **(reference)**; computed (`python -c "print(hex(0x02AFFE-32768), hex(0x02AFFE+32767))"`).
62. An instruction names a variable in two bytes where a full address takes four, and needs no relocation: when the data moves, A4 moves with it. Source: PRM 2, the displacement word against the absolute long address **(reference)**; `tools/hunk.py` (the code hunk carries 22 relocations, 17 into the data, against 4,198 operands relative to A4, claim 65).
63. `-$46ec(a4)` of chapter 2 is `0x02AFFE` − `0x46EC` = `0x026912`, `rand_seed_const`. Source: computed; chapter 2's fact sheet, claim 29.
64. The hand-written `rand_beam` reaches its variables through A4 the same way; the two kinds of code share one set of variables. Source: `re/Wings.lst`, `0x0203BE` (and `text_width`, `0x01591E`).
65. About one instruction in five has an operand relative to A4: of the code hunk's 21,332 instructions, 4,198 (the prose keeps "one in five"). Source: a count over `re/Wings.lst`: lines with an address below `0x022F4C` and an instruction (not `dc.`), 21,332; of them with an operand `$...(a4)`, 4,198.
66. Many of those are calls into the far-call table, 185 jump instructions at the start of the data hunk, each holding the full address of a routine (some routines have two slots); exactly, 659 calls and 13 jumps go through it, which the prose leaves out. Source: `grep` on `re/Wings.lst` (`jsr -$...(a4)` 659, `jmp -$...(a4)` 13); `SPEC.md` 3.2 (185 slots of `JMP abs.l` at `0x023000`–`0x023456`); `re/Wings.lst` `0x023000`–`0x023450` (`fatal_exit` and `rand_beam` with two slots each).
67. A call through the table such as `jsr -$7e1e(a4)` (`main`, `0x01000E`, four bytes) is one short instruction that reaches any routine from anywhere and needs no relocation of its own; the correcting is done once, in the table's 185 slots. Source: `re/Wings.lst` `0x01000E` (`4eac81e2`); `tools/hunk.py` (all 185 slots carry a relocation into the code, at slot + 2); PRM 2 **(reference)**.
68. With the calls relative to the program counter and the variables relative to A4, that is why the code hunk needs only 22 relocations. Source: derived from claims 62 and 65 to 67 and `re/Wings.lst` (calls such as `jsr $12570(pc)` at `0x010012`); PRM 2, program counter relative **(reference)**.
69. The calling convention: the caller pushes the arguments, the last first, 2 bytes for an int and 4 for a long or a pointer, and calls, which pushes the return address, 4 bytes; the result comes back in D0. Source: `SPEC.md` 3.2; `tools/oracle.py`, docstring; PRM 4, `JSR` **(reference)**.
70. Each of the 223 C routines begins with `link a5`, which builds its stack frame: it pushes the caller's A5, sets A5 to the stack pointer and moves the stack pointer down for the routine's variables; the caller's A5 and the return address, four bytes each, lie above A5, so the first argument is at `8(a5)`; the variables lie below A5. Source: `SPEC.md` 3.2 (LINK A5, the first argument at `8(a5)`); `grep -c 'link.w     a5' re/Wings.lst` gives 223; PRM 4, `LINK`, `UNLK` **(reference)**.
71. `record_at` returns, for a world x, the address of the map record under it, with `map_records`, the address of the map's first record, and `map_records_end`, the bound it checks against. Source: `re/names.txt` (`record_at`, "the map record under a world x, clamped to the list"); `re/notes/map.md`, "The file" (`map_records` the allocation, `map_records_end` its last record).

## The 16-bit int

77. In Manx Aztec C, as the game was built, an int is 16 bits, a long and a pointer 32; the compilers that build the port make an int 32 bits (zig cc for the WebAssembly core, Apple clang for the native library of the tests). Source: `SPEC.md` 3.2 and 2 (the two compilers); `tools/oracle.py`, docstring; wasm C ABI **(reference)**; Apple's LP64 model **(reference)**.
78. An int holds −32,768 to 32,767; one past the largest is the smallest. Source: computed (two's complement, 2^15); PRM 1 **(reference)**.
79. An enemy fighter sets the length of a turn from its distance from the player in pixels, times 100, divided by its speed; `muls.w` multiplies two 16-bit numbers into 32 bits, the compiled code keeps the low 16 bits, sign-extends them with `ext.l` and only then divides with `divs.w`; from a distance of 328 on the product would not fit, 32,800 would become −32,736, and a port that kept 32 bits would time the turn differently; whether a turn is ever timed at such a distance was not measured; the port does the same, bit for bit. Source: `re/notes/porting-m6.md`, "The tick: what part 2 ports" (the timing of a turn by the distance times 100); `src/enemy.c`, the header comment and `turn_in` (`muls, ext.l`); `re/notes/enemy.md`, the modes' flights (distances in pixels); PRM 4, `MULS` **(reference)**; computed (`python -c "print(328*100-65536)"`).
80. Among the rules of `SPEC.md` 7.1: no plain int for a game value but `int16_t`, `uint16_t`, `int32_t` and their kin; every change of width the listing shows (a sign extension, a product cut to 16 bits or kept at 32, a division that rounds toward zero with a 16-bit quotient); the signedness from the branch that reads the comparison, the 68000 having separate branches for signed and unsigned comparisons; wrap-around kept with an explicit cast, because a signed overflow is undefined in today's C and a compiler may assume it never happens; floating point never through `float` or `double`. The list is introduced with "among the rules": 7.1 also has the table read past its end, the flags a branch reads, `asr` and the division's traps. Source: `SPEC.md` 7.1; PRM 3 and 4, `Bcc` (`blt`, `bge` signed; `bcs`, `bhi` unsigned) **(reference)**; ISO/IEC 9899:2011, 6.5 paragraph 5 **(reference)** for the undefined overflow, on which an optimising compiler may build.
81. The game's floating point goes through the C library to the ROM's fast floating point, which the port redoes in integer code; chapter 14. Source: `re/notes/ffp.md`, "How the game reaches it" and "The port"; `SPEC.md` 3.4, the mathffp row; `book/BOOK.md` 3, chapter 14.
82. A register's upper half may hold a value a routine leaves for the next to read; the port must hand it on; chapter 9 tells how that was learnt. Source: `SPEC.md` 7.1 (the upper word); `book/BOOK.md` 3, chapter 9 ("the register carried as a long"). (Extended by claim 109.)
