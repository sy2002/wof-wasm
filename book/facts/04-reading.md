# Fact sheet: chapter 4, Reading the executable

Every claim the chapter makes, one line each, with its source, in the order of the chapter. A claim without a source goes to the list at the end and stays out of the draft. A general fact about the 68000 that the repository does not state is sourced in a reference work outside the repository, named with its section, and marked **(reference)**, so that the fact-check can weigh it; a fact about this game, its program, the listing or the project's tools is always sourced in the repository. One reference work is cited:

- *M68000 Family Programmer's Reference Manual*, Motorola (M68000PM/AD), cited as PRM with its sections 2.1 "Instruction Format" (an instruction is one word or more; the first, the operation word, specifies the operation, the effective addressing mode and so the instruction's length; extension words follow), 3 "Instruction Set Summary" and 4 "Integer Instructions" (`LINK`, `UNLK`, `MOVEM`, `DBcc`, `JSR`, `RTS`, `DIVS`).

Counts are of the branch's base, `3f9fb4c`, where `re/Wings.lst` is at `7e8225e`'s regeneration; every one was counted by the command named in "Counts and where they were counted". The status counts of `re/functions.csv` are a snapshot of a hand-edited column and are given exact with that commit.

## Opening

1. By the chapter's end the reader knows what a disassembler does and what the listing gives that the program's bytes do not; how the routines got their names and why the names live in a file of their own; what the inventory records; what a control-flow skeleton is for; how compiled C and hand-written assembly look in the listing and why the port must tell them apart; what could be recognised and how; and why a reading is a claim until the running original confirms it. Source: `book/BOOK.md` 3, chapter 4; the controller's task.

## A program of numbers

2. Chapter 3's code hunk is 77,644 bytes of machine code with no symbol in it: nothing in the file names a routine or a variable, or says where one instruction ends and the next begins. Source: chapter 3 (`tools/hunk.py`, `syms= 0`); `SPEC.md` 3.2.
3. The port is written from the original's code, routine by routine, not from what the game seems to do; that needs the code in a form people can read. Source: `CLAUDE.md`, Rules ("Port from the disassembly, not from assumptions"); `SPEC.md` 7.4, steps 1 to 3; chapter 1.
4. A disassembler is the tool that turns machine code back into assembly language. Source: chapter 2 (its first mention); `SPEC.md` 4 (`tools/disasm.py`, `tools/m68kdis.py`); `tools/disasm.py`, docstring.
5. A 68000 instruction is one word of 16 bits or more: the first, the opcode (Motorola's operation word), names the operation and how its operands are found, and so how many words follow; the instruction's own bytes say how long it is. Source: PRM 2.1 **(reference)**.
6. In this program every instruction is 2, 4, 6 or 8 bytes long. Source: the listing's byte column counted (7,486 of 2 bytes, 12,196 of 4, 1,584 of 6, 66 of 8).
7. Decoding one instruction from a known start is mechanical; the project leaves it to Capstone, a disassembly library pinned in `requirements.txt`. Source: `SPEC.md` 2 (`capstone` 5.0.9, "disassembler"); `tools/disasm.py` (`Cs(CS_ARCH_M68K, CS_MODE_M68K_000)`, `decode()`).
8. The hard part is where to start: the code hunk also holds the strings, after the routine that uses them, and tables; decoded from a wrong place, bytes still give instructions, and printable text decodes as valid 68000 code. Source: `SPEC.md` 3.2 (string literals in the CODE hunk after the routine that uses them; switch tables); `tools/disasm.py`, `looks_like_code` ("prose decodes as valid 68k").
9. So `tools/disasm.py` follows the control flow, the order in which the program's instructions run, set by its branches, jumps, calls and returns: it starts where code certainly begins (the program's first instruction, the 185 slots of the far-call table, every `link a5`), decodes on from each start, follows a branch both ways and a call into the routine it calls, and stops a path at a return or an unconditional jump. Source: `tools/disasm.py`, docstring ("How code is found", 1 to 4), `Analysis.analyse` and `Analysis.run` (`TERMINATORS`, `Bcc`, `DBcc`, `JSR`/`JMP`); `SPEC.md` 3.2 (the far-call table).
10. A call through the far-call table (`jsr -$7e1e(a4)`) is followed to the routine its slot holds; a `switch` of the compiled C is followed through its table of offsets (four such tables, 44 cases); an address the code takes relative to the program counter is tried as code when it is not a string. Source: `tools/disasm.py`, docstring 2 to 4, `far_target`, the switch branch of `run`; the listing (`switch case` lines: 44 in 4 tables).
11. What no path reaches is either text (a run of at least twelve printable bytes, mostly letters) or is tried last, in a gap sweep, and accepted as code only if it decodes cleanly to a return or a jump and its first bytes are not almost all printable; 55 blocks were found that way and are marked "found by gap sweep" in the listing, 45 of them as routines of their own. Source: `tools/disasm.py`, `text_run` (12 bytes, 70 per cent letters), `looks_like_code` (95 per cent printable refused), the gap sweep in `analyse`; the run's line "616 (C: 223, asm: 393), 55 found by gap sweep"; `grep` on the listing (45 routine headers with the mark); `SPEC.md` 4, Listing conventions (blocks found by gap sweep are uncalled routines or reached only through computed addresses).
12. Without the guard against printable bytes, text would enter the inventory as routines that do not exist. Source: derived from claim 8 and `tools/disasm.py`, `looks_like_code`.
13. The result: of the code hunk's 77,644 bytes, 73,792 (95.0 per cent) are instructions, 3,725 strings and text, 88 switch tables, and 39 bytes stay unexplained. Source: `tools/disasm.py`'s own report, run into the scratchpad (`--out`), identical to the committed files; `SPEC.md` 3.2 ("all but 39 bytes").
14. The run takes about two seconds. Source: `SPEC.md` 4 ("about 2 seconds"); measured 1.7 s.

## The listing, line by line

15. The listing, `re/Wings.lst`, is the program written out by the disassembler: 32,434 lines, 21,332 of them instructions, each with its address in the fixed load layout, its bytes, the instruction and, after a semicolon, what the tool knows of it. Source: `wc -l re/Wings.lst`; the count of chapter 3's fact sheet, claim 65, repeated (lines with an address below `0x022F4C` that are not `dc.`); `tools/disasm.py`, the line format `'%06x  %-20s %-10s %s'`.
16. Two more lines in the code carry bytes that decode as no 68000 instruction (`$f35f`) and stand as data. Source: the count (21,334 lines with bytes, two of them `dc.w $f35f` at `0x021F6E` and `0x022A0A`). (In the sheet; the prose leaves it out.)
17. The listing's first lines name the tool, the files it reads and the layout: CODE `0x010000`–`0x022F4C`, DATA `0x023000`–`0x027FF0`, A4 `0x02AFFE`, the far-call table `0x023000`–`0x023456`. Source: `re/Wings.lst`, lines 1 to 3.
18. Every routine opens with a header: a rule of `=` signs, its name, its kind in brackets, for compiled C the size of its frame, its far-call slot if it has one, the comment from `re/names.txt`, and the routines that call it; then its name as a label. Source: `tools/disasm.py`, the header code (`hdr`, `frame=`, `far-call slot`, `callers:`); `SPEC.md` 4, Listing conventions.
19. The excerpt is the start of `main` (`0x010006`–`0x010046`): its header says `[asm]` and far-call slot `-32760(a4)`, its comment names the outer loop at `loc_010066` and the inner loop at `loc_01010e`, and its one caller is `sub_021fa8`, a routine without a name. Source: `re/Wings.lst` `0x010006`–`0x010046` and the header above it; `re/names.txt` (`010006 main`).
20. A label is a name the listing gives an address that a branch or a call leads to, on a line of its own, ending in a colon: a routine's name, or `loc_` and the address for a place inside a routine without a name of its own; the listing has 2,116 `loc_` labels. Source: `tools/disasm.py`, `name_of` (`loc_%06x`) and the label lines; the count.
21. The comments the tool writes, by kind: an operand through A4 gets the variable's name, or `g_` and its address when it has none (`IntuitionBase`, `outside_mission`, `g_024cac` in the excerpt); a call through the far-call table gets an arrow and the routine its slot holds (`-> sub_01aa50`); a call relative to the program counter gets the routine's name (`open_libraries`); a call into a library gets the library and the routine (`intuition.CloseWorkBench`); a long the loader corrects gets the name or the string it points to (`demo_file_name | "wofdemo"`). Source: `tools/disasm.py`, the notes of each instruction line (`re_a4`, `far_target`, `re_pc`, the relocations, the OS call); `re/Wings.lst` `0x010006`–`0x010046`.
22. The listing names no hardware register: the first instruction of `main` sets a bit at `$bfe001.l`, an address of one of the CIAs, given as a number; the tool names only what is reached through A4, the program counter, a relocation or a library. Source: `re/Wings.lst` `0x010006` (no comment); `tools/disasm.py` (the four kinds of note); chapter 2 (`0xBFE001`, CIA-A's port).
23. Of the 3,526 instructions that name a variable through A4, 2,579 name it and 947 give a `g_` address; 369 different unnamed variables are reached so. Source: the count over the instruction lines (A4 operands other than `jsr`/`jmp` through the far-call table; the first note `g_` or not).
24. 672 instructions go through the far-call table, each resolved to its routine. Source: `grep '; -> '` over the instruction lines (659 calls, 13 jumps, chapter 3's fact sheet, claim 66).
25. In the excerpt `main` checks how many arguments it was started with (the word at `$4(a7)`) and, with more than one, stores the address of the name `wofdemo` in `demo_file_name`: started with an argument, the game records a demo; chapter 17. Source: `re/Wings.lst` `0x01002C`–`0x01003A`; `re/notes/headless.md`, "What runs and what does not" (`argc` above 1 records a demo, `0x01002C`); `re/notes/demo.md`; `book/BOOK.md` 3, chapter 17. (The prose may leave the demo out.)
26. A call into the operating system is named in two steps: `re/libbases.txt` says which variables hold a library's address (five: exec, intuition, graphics, dos, mathffp), and the tool watches A6 being loaded from one; the offset of the call is looked up in the library's fd file, a list of its routines in order, the first at offset 30 below the library's address and each further one six bytes on. Source: `re/libbases.txt`; `tools/disasm.py`, `load_fd` (`bias` 30, `+= 6`), the OS call code (`cur_a6`, `0x4EAE`, `0x4EEE`); `tools/fd/ORIGIN.txt` (the fd files copied unmodified from amitools 0.8.1); `tools/fd/dos_lib.fd` (`Open`, `Close`, `Read` first, so `-$1e`, `-$24`, `-$2a`).
27. A library's address is called its base, which a program keeps in a variable and loads into A6 to call one of the library's routines at a fixed offset below it. Source: `re/libbases.txt`, its header ("library base variable"); `tools/disasm.py` (`cur_a6`; `movea ... , a6`); the glossary's entry Library (chapter 2).
28. Why the calls into the system are named: each is a place where the port must answer for the operating system, which it replaces (the files, the memory, the display), chapter 2's table. Source: `SPEC.md` 3.4 (the operating system's use, each with the port's answer) and 6.6 (what is replaced or dropped); chapter 2, "The little of AmigaOS the game uses".
29. The code makes 137 calls or jumps into a library; 130 are named (exec 53, dos 48, graphics 25, intuition 4); seven keep only their offset, where A6 was loaded in a way the tool does not follow. Source: the count over the instruction lines (`jsr`/`jmp -$..(a6)`, the note with a library's name or `a6=?` and `base@`).
30. The DATA hunk follows the code in the listing: the far-call table's 185 slots, each with the routine it holds, then the variables by name, with their starting values. Source: `tools/disasm.py`, the DATA part; `re/Wings.lst` from the line "DATA hunk".
31. The texts are summarised on purpose: a string the code points to is shown to its first 48 characters, and each of the six long runs of text that nothing points to, 2,278 bytes in all, the longest the story of 2,120 bytes, is one line with its length; the listing, which anyone can read in the repository, is not a second copy of the game's texts, and the port reads them from the program when it is built (chapter 3). Source: `tools/disasm.py` (`STR_MAX = 48`, `dc.b <text, N bytes>`); the count of the `<text,` lines; `re/tables.toml` (`story_text`, `0x017494`); `CLAUDE.md`, Rules ("summarised in the listing on purpose"); `SPEC.md` 1 (published); chapter 3 ("Read from the executable, never retyped").

## Names

32. Every name in the listing was given by the project: the program kept none (chapter 3). Source: chapter 3, claim 50 of its sheet; `SPEC.md` 4, Naming workflow.
33. `re/names.txt` is the one hand-maintained list: a line per address, the address in hexadecimal, a name and, after a semicolon, a comment. Source: `re/names.txt`, its first line; `tools/disasm.py`, `load_names`; `SPEC.md` 2 ("hand-maintained names for code and data addresses").
34. It holds 798 names: 449 in the code (445 of the 616 routines and 4 places inside routines) and 349 variables and tables in the data; 712 of the lines carry a comment; the file is 883 lines in 26 sections. Source: `tools/disasm.load_names` counted; the routines from `re/functions.csv` with `csv.DictReader`; `grep -c '' re/names.txt`; the lines beginning `# ----`.
35. A routine without a name is `sub_` and its address (171 of the 616), a place inside one `loc_`, a variable `g_`, a string `str_`. Source: `tools/disasm.py`, `name_of`; `re/functions.csv` (171 names beginning `sub_`).
36. Why a file of its own: the listing is made by the tool and never edited by hand, so that it can be made again at any time from the program, the tool and the names; a name written into the listing would be lost at the next run. One line in `re/names.txt` reaches the listing, the skeletons, the inventory and the headless original's reports alike. Source: `CLAUDE.md`, Rules ("Never edit `re/Wings.lst` by hand. Put names in `re/names.txt`"); `SPEC.md` 4, Naming workflow ("The listing, the skeletons and the inventory pick the name up everywhere"); `tools/disasm.py` (writes the whole file); `re/notes/headless.md`, "Change report, entropy log, schedule" ("an address with an entry in `re/names.txt` gets it").
37. When a routine or a variable is understood, it gets its name in `re/names.txt` and the listing is made again. Source: `SPEC.md` 4, Naming workflow; 7.4, step 2.
38. `tests/test_generated.py` makes the listing and the inventory again from the committed names into a directory of its own and compares them with the committed files byte for byte, so that the listing a reader browses is always what the tool makes. Source: `tests/test_generated.py`, docstring and `test_the_listings_are_their_regeneration`; `CLAUDE.md`, Rules; checked: a regeneration into the scratchpad is identical.
39. A name is a claim of what a thing is, and a comment beside it often says how it was known; the names are the vocabulary the notes, the port's comments and the tests share. Source: `re/names.txt` (comments such as `see re/notes/input.md`); `src/*.c` (`orig 0x......` and names); `re/notes/` (names with addresses throughout). (The prose keeps it short.)

## The inventory

40. A routine is a piece of the program that is called, does one job and returns to its caller; the inventory counts as one routine everything from an entry point the disassembler found (a call's target, a far-call slot, a `link a5`, a gap-sweep block) to the next one. Source: `tools/disasm.py` (`funcs` seeded by calls, slots, `link`, the sweep; `fend`, the span to the next routine); chapter 1 ("616 routines").
41. The routine inventory, `re/functions.csv`, is made by the same run: one row per routine, 616 rows, with its address, its name, its kind, its span in bytes to the next routine, for C its frame and the offsets of the arguments it reads from A5, its far-call slot, how many routines call it, the routines it calls, the library routines it calls, how many variables it touches, the strings it uses, and its status. Source: `tools/disasm.py`, the rows (`addr`, `name`, `kind`, `span`, `frame`, `a5_args`, `far_slot`, `callers`, `calls`, `os_calls`, `globals`, `strings`, `status`); `re/functions.csv`, header and 616 rows.
42. The spans add up to the whole code hunk, 77,644 bytes: every byte belongs to one routine, strings and text included. Source: `re/functions.csv`, the spans summed.
43. A routine of the inventory is not always one routine of the program: `ship_at_offset` falls into the instructions that follow it, and the inventory cuts it in two, a span of 4 bytes and the rest. Source: `re/notes/objects.md`, "What the width of a port looks like" (`0x014A4E`, a span of 4, about 150 bytes together).
44. Read it with a CSV reader: the string column holds commas. Source: `CONTROLLER.md`, "Pitfalls that cost time" (`cut` miscounts); `re/functions.csv`. (For the developer.)
45. What the inventory is for: it is the list the work is planned on, by kind and size, the list the observation of the original hooks (every routine's first instruction), and the page of this book's appendix. Source: `re/notes/objects.md`, "What the width of a port looks like" ("For planning M5 and M6: the routines of each kind, their sizes"); `re/notes/porting-m4.md`, "What decides what is ported: the reach map" ("a hook on the first instruction of every routine of `re/functions.csv`"); `book/docs/routines.md`.
46. The status column is the one column written by hand; every regeneration carries it over, and a routine new to the inventory gets `todo`. Source: `SPEC.md` 7.4 (the last paragraph); `tools/disasm.py` (`old_status`, default `'todo'`); `CLAUDE.md`, Rules.
47. The values: `verified`, ported and held to the original under the oracle (chapter 5); `ported`; `partial`, ported as far as the recorded runs of the game reach it, the rest marked so that a run reaching it fails (chapter 8); `replace`, the port does the job its own way (the system glue, memory, the copper lists, the floating point's calls); `drop`, not needed (the crack's screen, the debug reporters, routines the port has no use for); `todo`, no status set. ## The skeleton of a routine

51. A control-flow skeleton is a routine with only the lines that decide where it goes: its labels, calls, branches, tests and compares, and returns. `tools/skel.py` prints it from the listing, by name or address; `--all` prints the whole routine. Source: `tools/skel.py`, docstring and `KEEP`; `SPEC.md` 4.
52. What it is for: it is the first step of porting a routine, before reading it in full, because the shape of a routine (its loops, its exits, what it calls, what it asks the system for) usually says what it does. Source: `SPEC.md` 7.4, step 1; `tools/skel.py`, docstring ("usually enough to see what a routine does before reading it in full").
53. `map_load` (`0x012ADC`, hand-written, 226 bytes) is 77 lines in the listing and 22 as a skeleton. Source: `tools/skel.py map_load | wc -l` and `--all | wc -l`; `re/functions.csv` (`012adc`, `asm`, span 226).
54. Read from its skeleton: it clears the airfields; runs a loop with `dbra`, which here adds up the missions of the ranks before the one played to find the mission's map; opens the file (`dos.Open`); reads twice (`dos.Read`), the two numbers at the map file's head (chapter 3); asks for memory and, if none is given, branches away to the routine that ends the program; reads the records; closes the file; calls `map_scan`. Source: `tools/skel.py map_load`; `re/Wings.lst` `0x012ADC`–`0x012BBC` (`missions_per_rank`, `rank_played`, `mission_number`; `loc_0124d8` is `jmp -> fatal_exit`); `re/names.txt` (`map_load`: "opens maps/... .map, reads the two longs and the records, then `map_scan`"); `re/notes/map.md`, "The file"; chapter 3 (two numbers of four bytes, then the records).
55. `dbra` counts a register down and branches back until it passes below zero. Source: PRM 4, `DBcc` **(reference)**.
56. Fifty-five lines the skeleton leaves out are the arithmetic and the moves between: what they compute is read afterwards, with the shape already known. Source: claim 53 (77 − 22); `SPEC.md` 7.4, step 1 ("then read the routine in the listing").

## Compiled C and assembly written by hand

57. The two kinds look different in the listing, and the port must know which is which: a compiled routine follows the compiler's calling convention, so the oracle calls it with its arguments on the stack, while a hand-written one takes them in registers that its caller sets, and the oracle must set those; compiled code's arithmetic is the 16-bit int's, whose widths the port keeps (chapter 3), while hand-written code may leave a value in a register for the next routine to read (chapter 9). Source: `tools/oracle.py`, docstring (stack arguments with `W` and `L`) and `SPEC.md` 4, "The oracle" (`regs=`); `SPEC.md` 7.1 (the widths; the upper word "a register a routine leaves as a long reaches the next routine's upper word"); `book/BOOK.md` 3, chapter 9 ("the register carried as a long").
58. The project's rules treat the hand-written first third separately: a routine there not understood after a full reading stops the work for a report. Source: `CLAUDE.md`, Session protocol ("a routine in the hand-written assembly region (`0x010000`–`0x015D62`) is not understood after reading it in full").
59. A compiled routine: `colour_lerp` (`0x016FF6`, one step of a 16-step fade) begins with `link.w a5, #$fffe`, a frame of two bytes for one variable at `-$2(a5)`; reads its three arguments at `$8(a5)`, `$a(a5)` and `$c(a5)`; computes each colour component with `muls.w`, `ext.l` and `divs.w`, the 16-bit int's idioms; leaves its result in D0; ends with `unlk a5` and `rts`. Source: `re/Wings.lst` `0x016FF6`–`0x017082`; `re/names.txt` (`colour_lerp`: "(step 0..15, from, to) per 4-bit component"); `src/iff.c`, `wof_colour_lerp`, comment ("one step of a 16-step fade"); chapter 3 (`link a5`, `8(a5)`, `ext.l`, `divs.w`).
60. Its third component divides a 32-bit product by 15 through a call to a helper at `0x0223CC` (unnamed, `sub_0223cc`), reached through the far-call table, because the 68000's `divs.w` divides a 32-bit number by a 16-bit one and gives a 16-bit quotient. Source: `re/Wings.lst` `0x01706A`–`0x017070` (`jsr -$7c3e(a4) ; -> sub_0223cc`), `0x0223CC`–`0x0223F2` (signs taken off, `sub_022424`, the sign put back); `src/iff.c`, `wof_colour_lerp` ("red divides the full 32-bit product"); PRM 4, `DIVS` **(reference)**.
61. Its caller hands it its arguments as the compiler does: `fade_to` pushes three words with `move.w ..., -(a7)`, the last argument first, calls, then takes the six bytes off the stack with `addq.w #$6, a7` and uses D0. Source: `re/Wings.lst` `0x017124`–`0x017156`; `SPEC.md` 3.2 (right to left, 2 bytes an int).
62. A hand-written routine: `text_width` (`0x01591E`, the width of a text in the game's font) has no frame; it saves every register it might change with one `movem.l d1-d7/a0-a6, -(a7)`; takes its arguments in registers, the text's address in A0 and its length less one in D0; uses A5, the compiled code's frame pointer, for its own purpose, the address of the font; loops with `dbra`; leaves the width in D0; restores the registers and returns with `rts`. Source: `re/Wings.lst` `0x01591E`–`0x015954`; `re/names.txt` (`text_width`: "A0 = string, D0 = length - 1 -> D0 = pixel width"); `src/font.c`, `wof_text_width`; PRM 4, `MOVEM`, `DBcc` **(reference)**.
63. Its caller, `text_render`, also hand-written, takes one off the length in D0, saves D0 on the stack itself and calls; the convention is the routine's own, written in the listing's comment and nowhere else. Source: `re/Wings.lst` `0x01595E`–`0x01596C`; `re/names.txt` (the comment of claim 62).
64. How the two were told apart: the inventory's kind is decided by one rule, a routine whose first instruction is `link a5` is C, any other is assembly; 223 C, 393 assembly. Source: `tools/disasm.py` (`kind = 'C' if img.u16(a) == 0x4E55 else 'asm'`); `re/functions.csv` with `csv.DictReader`; `grep -c 'link.w     a5' re/Wings.lst` (223), `unlk a5` 223.
65. The rule holds because the compiler opens every function with `link a5`, and the count agrees with the 223 C routines of the specification. Source: `SPEC.md` 3.2 ("C routines start with `LINK A5`"; "616 routines, of which 223 are C").
66. Source: `re/functions.csv` by address and kind (205; 187 C and 61 asm to `0x0209BC`; 25 asm to `0x0215D8`; 36 C and 102 asm from `0x0215D8`); `SPEC.md` 3.2 (the layout; the blitter library); `re/names.txt` (`sound_init`, `audio_irq`, `soundfx_vblank`, `draw_dashboard`, `input_handler`, `rand_beam`, `rpck_unpack`, `sprintf`, `strcpy`, `os_dos_open`).

## What went wrong

80. (What went wrong) A note once said the last four records of every map are left uninitialised on a real machine, resting on how the headless original's memory stub behaved. Reading the routine the game calls for memory, its allocator at `0x020874`, showed `bset #$10,d0` at `0x020884`: bit 16 of the flags it hands `AllocMem` is `MEMF_CLEAR`, so every block the game asks for comes back cleared and the four records are zero on the machine as in the harness. The port's arena hands out zeroed memory since, and a test holds it. The lesson: a claim about the original rests on the original's code, not on the instrument's stand-in for the system. Source: commit `ba7ea44` ("The old passage rested on a stub's behaviour instead of on the callee"); `re/notes/map.md`, "The file" (`0x020874`, `0x020884`, `MEMF_CLEAR`, "the arena has to hand out zeroed memory"); `re/notes/porting-m4.md`, "Where mission memory lives" (the arena's test); `src/mem.c`.
81. The loader reads eight bytes more than the file holds, so the last four records of every map never come from the file. Source: `re/notes/map.md`, "The file".
