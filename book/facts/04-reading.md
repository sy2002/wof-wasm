# Fact sheet: chapter 4, Reading the executable

Every claim the chapter makes, one line each, with its source, in the order of the chapter. A claim without a source goes to the list at the end and stays out of the draft. A general fact about the 68000 or the Amiga that the repository does not state is sourced in a reference work outside the repository, named with its section, and marked **(reference)**, so that the fact-check can weigh it; a fact about this game, its program, the listing or the project's tools is always sourced in the repository. Two reference works are cited:

- *M68000 Family Programmer's Reference Manual*, Motorola (M68000PM/AD), cited as PRM with its sections 1 "Introduction" (the programming model, the program counter), 2.1 "Instruction Format" (an instruction is one or more words; the first, the operation word, specifies the operation, the effective addressing mode and so the instruction's length; extension words follow; on the 68000 an instruction is one to five words), 2.2 (program counter indirect with displacement) and 4 "Integer Instructions" (`LINK`, `UNLK`, `MOVEM`, `DBcc`, `JSR`, `RTS`, `DIVS`).
- *Amiga Hardware Reference Manual*, Commodore-Amiga, third edition (Addison-Wesley, 1991), cited as HRM with its appendix on the 8520 CIAs' port assignments (CIA-A port A, bit 1, the power LED's line) and its chapter on the audio hardware (the low-pass filter switched with the LED). The fact was handed to the chapter by the controller as a reference fact for the fact-check to weigh.

Counts are of the branch's base, `3f9fb4c`, where `re/Wings.lst` is at `7e8225e`'s regeneration; every one was counted by the command named in "Counts and where they were counted". The status counts of `re/functions.csv` are a snapshot of a hand-edited column and are given exact with that commit; the prose rounds them, and the figure's legend carries them at build time. By the owner's rule on numbers, the prose keeps about three numbers a sentence at most, puts clusters into a table or a caption and leaves derived numbers out; this sheet keeps every figure exact.

## The program as numbers

3. Nothing in the code hunk names a routine or a variable or says where one begins. Source: claim 2; `tools/hunk.py`.
4. The port is written from the original's code, routine by routine, not from what the game seems to do, as chapter 1 said; that needs the code in a form people can read. Source: chapter 1 ("The port is not a reconstruction of what the game seems to do; it is a translation of what its code does"); `SPEC.md` 7.4, steps 1 to 3; `CLAUDE.md`, Rules ("Port from the disassembly, not from assumptions"), cited in the developer's sidebar.
5. A disassembler is the tool that turns machine code back into assembly language. Source: chapter 2 (its first mention); `SPEC.md` 4 (`tools/disasm.py`); `tools/disasm.py`, docstring.
6. A 68000 instruction is one to five words of 16 bits: the first, the opcode (Motorola's operation word), names the operation and how its operands are found, and so how many words follow. Source: PRM 2.1 **(reference)**.
7. Decoding one instruction from a known start is mechanical; the project leaves it to Capstone, a disassembly library pinned in `requirements.txt`. Source: `SPEC.md` 2 (`capstone` 5.0.9, "disassembler"); `tools/disasm.py` (`Cs(CS_ARCH_M68K, CS_MODE_M68K_000)`, `decode()`); Capstone's site, fetched once (M68K among its architectures).
8. Instructions have no fixed length, in this program 2, 4, 6 or 8 bytes; a decode from a wrong byte does not stop but gives nonsense that still looks like instructions. Source: the listing's byte column counted (7,486 of 2 bytes, 12,196 of 4, 1,584 of 6, 66 of 8); PRM 2.1 **(reference)**; `tools/disasm.py`, `looks_like_code` (a candidate is decoded instruction by instruction and judged by where it ends).
9. The code hunk also holds the strings, after the routine that uses them, and tables between routines; printable text decodes as valid 68000 code; a decoder running straight through would read every message as instructions. Source: `SPEC.md` 3.2 (string literals in the CODE hunk after the routine that uses them; switch tables); `tools/disasm.py`, `looks_like_code` ("prose decodes as valid 68k"); `tools/m68kdis.py` (the straight decoder, which decodes whatever it is given).
10. `tools/disasm.py` follows the control flow, the order in which the instructions run, set by branches, jumps, calls and returns: it starts at the program's first instruction, at every routine the far-call table points to and at every `link a5`; decodes on; follows a branch both ways and a call into its routine, through the far-call table where the call goes that way; ends a path at a return or an unconditional jump. Source: `tools/disasm.py`, docstring ("How code is found", 1 and 2), `Analysis.analyse` (the seeds) and `Analysis.run` (`TERMINATORS`, `Bcc`, `DBcc`, `JSR`/`JMP`, `far_target`); `SPEC.md` 3.2.
11. The sorting of what no path reached, in its order: first, wherever the program holds the address of a place in the code (an operand relative to the program counter, or a relocated long outside the far-call table), the place is taken as a string if it reads as one and tried as code otherwise; then a sweep through the gaps, which first sets aside a run of at least twelve printable bytes, at least 70 per cent of them letters or spaces, as text; then any other gap counts as code only if it decodes cleanly up to a return or a jump, or runs into code already found, and its first bytes are not 95 per cent printable or more. Source: `tools/disasm.py`, docstring steps 3 to 5; `analyse` (the `refs` loop with `cstring` and `looks_like_code`, then the sweep: `text_run` before `looks_like_code`); `text_run` (12 bytes, letters or spaces 70 per cent); `_looks_like_code` (a terminator, or an address already decoded); `looks_like_code` (95 per cent printable refused).
12. Which rule keeps text out of the inventory: the text-run rule. The fact-check ran the analysis with the 95 per cent guard off and got the same 616 routines and 55 blocks; without the text-run rule one more routine appears. The prose states the rules in their order and draws no counterfactual. Source: the controller's fact-check of the draft (run in memory over `tools/disasm.py`); `tools/disasm.py`.
13. The sweep found 55 blocks of code that no path reaches, 45 of them routines of their own and the rest places inside routines: uncalled code, or code reached only through an address computed at run time; two of the 45 have a caller in the inventory (`sub_01f946`, `sub_01fc2a`). Source: `tools/disasm.py`'s report ("55 found by gap sweep"); `grep` on the listing (45 routine headers with the mark, 10 label lines); `SPEC.md` 4, Listing conventions ("code that nothing references by control flow (uncalled library routines or routines reached only through computed addresses)"); `re/functions.csv` (callers of the 45).
14. The table: instructions 73,792 bytes, strings and text 3,725, the tables of four `switch` statements 88, unexplained 39; nearly every byte accounted for. Source: `tools/disasm.py`'s own report, run into the scratchpad (`--out`), identical to the committed files; the listing (`switch case` lines: 44 cases in 4 tables); `SPEC.md` 3.2 ("all but 39 bytes").

## Compiled C and assembly written by hand

64. A compiled routine keeps to the compiler's calling convention (arguments on the stack, result in D0, a 16-bit int, the widths of chapter 3); a hand-written routine has its own, from its registers, and may leave a value in a register for the next one, which chapter 9 shows the port had to learn. Source: `SPEC.md` 3.2 and 7.1 (the upper word: "a register a routine leaves as a long reaches the next routine's upper word"); `tools/oracle.py`, docstring; `book/BOOK.md` 3, chapter 9.
65. A compiled routine's arguments are where the convention says; a hand-written routine's can be known only by reading it whole, so the oracle is told the registers for each one by hand. Source: `tools/oracle.py` (`call(..., regs=None, ...)`: "`regs` optionally presets registers, e.g. {'d0': 1, 'a0': ptr} for asm routines"); `SPEC.md` 4, "The oracle". (The earlier "every hand-written routine is read in full and never guessed at" is dropped: 162 hand-written routines are `todo`.)
66. `colour_lerp` (`0x016FF6`) takes the step (0 to 15), the colour it starts from and the colour it goes to. Source: `re/names.txt` (`colour_lerp`: "(step 0..15, from, to) per 4-bit component; step 15 returns to"); `src/iff.c`, `wof_colour_lerp` (`step`, `from`, `to`).
67. An Amiga colour is three fields of four bits, red, green and blue, which the masks `$f00`, `$f0` and `$f` pick out. Source: `re/Wings.lst` `0x017014`–`0x01705C` (the masks); `src/iff.c`, `wof_colour_lerp`, comment (the components); chapter 2 (4,096 colours).
68. It opens with `link.w a5, #$fffe`, a frame for one variable at `-$2(a5)`; its arguments at `$8(a5)`, `$a(a5)`, `$c(a5)`; at step 15 (`cmpi.w #$f, $8(a5)`) it returns the target at once through the `unlk a5` and `rts` near its top (`0x017006`), to which its last instruction (`0x017082`, `bra.b $17006`) also branches back. Source: `re/Wings.lst` `0x016FF6`–`0x017082`.
69. Each field by the same few instructions written out three times, blue first, where a person would write a loop; blue and green cut their product to 16 bits with `ext.l` before `divs.w` (chapter 3's idiom); red's difference, up to 3,840 (`0xF00`), times the step would not fit a 16-bit int (15 x 3,840 is 57,600), and the compiled code keeps the product whole and divides it through a helper near the end of the code (`0x0223CC`, unnamed, through the far-call table), the compiler's own division of a long; the port keeps both widths. Claimed as the arithmetic the listing shows, not as the authors' thought. Source: `re/Wings.lst` `0x017010`–`0x01707A` (three blocks; `muls.w`, `ext.l`, `divs.w` in the first two; `muls.w`, `moveq #$f, d1`, `jsr -$7c3e(a4) ; -> sub_0223cc`, `and.l` in the third), `0x0223CC`–`0x0223F2` (signs off, `sub_022424`, sign back); `src/iff.c`, `wof_colour_lerp` ("blue and green divide a 16-bit product with divs.w, red divides the full 32-bit product"); computed.
70. Its two callers, `fade_to` (calls at `0x017140`, `0x017188`) and `fade_to_pair` (`0x0172BE`, `0x0172FC`, `0x017346`), push three words, the last argument first, call, take the six bytes off with `addq.w #$6, a7` after each of the five calls and use D0. Source: `re/Wings.lst` `0x017124`–`0x017156` and the four other call sites; the `colour_lerp` header (callers `fade_to`, `fade_to_pair`); `SPEC.md` 3.2.

72. `text_width` (`0x01591E`): no frame; one `movem.l d1-d7/a0-a6, -(a7)` saves every register but D0 and A7, the stack pointer, so that its caller's values survive; the text's address in A0, its length less one in D0, because `dbra` runs once more than its count; A5 for its own purpose, the loaded font file (`font_file`); per character: skipped if above the last or below the first character of the font, else its width from the font's table at `4(a5, d2.w)`, a zero width counting ten, plus one; the width in D0; registers restored; `rts`. Source: `re/Wings.lst` `0x01591E`–`0x015954`; `re/names.txt` (`text_width`: "A0 = string, D0 = length - 1 -> D0 = pixel width"); `src/font.c`, `wof_text_width` and its comment ("the sum over the characters in range of width + 1, where a width of 0 counts as 10"); PRM 4, `MOVEM`, `DBcc` **(reference)**.
