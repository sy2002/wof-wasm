## Opening

1. By the chapter's end the reader knows how the whole original program runs without a screen under the oracle's emulator, what stands in for the machine and why none of it can change the game's logic, how time, input and chance reach the program, what a run leaves behind, why two runs are identical, and why the wall clock must never shape a run. Source: `book/BOOK.md` 3, chapter 6; the controller's task; claims below.

## The whole program, not one routine

2. The oracle (chapter 5) runs one routine on inputs the test chooses, a state the test builds; a mission is the whole program, in which the order and the moment of the routines' calls, the state one routine leaves for the next and the interrupts between them decide what happens; most of the game's routines read the world, the state of the game. Source: `book/docs/part-1/oracle.md`, "What verified means" ("the order and the moment in which the game calls its routines", "held by the comparisons of whole runs"); `SPEC.md` 3.3, "Passes are not pure rendering" (what crosses between pass and tick); `re/notes/passes.md`, "What the question is".
3. So the original program itself runs, from its `main` routine on, under the same emulator as the oracle, with nothing of its logic rewritten: initialisation, the title sequence, the rank selection, the mission setup, the inner loop, the VBlank servers and the key handler are the original's own code. Source: `re/notes/headless.md`, opening and "What runs and what does not" ("**No game logic is re-implemented.**"); `tools/headless.py`, docstring; `SPEC.md` 8, row "Whole game, logic".
4. It is built on the oracle: `Headless.__init__` makes an `Oracle(a4=0x02AFFE)`, the same Unicorn 68000 with the program at the fixed load layout, and the oracle installs the correction of the memory-form shift, so the headless original carries it too. Source: `tools/headless.py`, `Headless.__init__` (`self.o = Oracle(a4=A4)`); `tools/oracle.py`, `Oracle.__init__` (`m68k_fix.install`); `re/notes/headless.md`, "Unicorn, as it behaves here", last point.
5. `main` (`0x010006`) is entered the way the C startup enters it: A4 set, `SysBase` and `DOSBase` filled in, a 16-bit `argc` of 1 and `argv` on the stack; the C startup itself (`0x021F2E`) is not run. Source: `re/notes/headless.md`, "What runs and what does not"; `tools/headless.py`, `Headless.__init__`, the last block (`MAIN`, the stack, `argc`).
6. The instrument is milestone M2's, accepted when per-tick dumps are produced for a scripted input stream and a fixed entropy stream and two runs give identical dumps. Source: `SPEC.md` 9, the table, row M2.
7. It is the reference the port is compared with tick by tick (chapter 8), and the instrument by which the notes "observe" (chapter 4). Source: `SPEC.md` 8, rows "Whole game, logic" and "Mission, pass by pass"; `book/docs/part-1/reading.md`, "A reading is a claim" ("chapter 6 tells how").

## What stands in for the machine

8. The operating system is answered by stubs, one Python method per library call, named after the library and the function; the program's call lands in a fake library base whose every jump-table slot is an `rts`, a code hook over that area parks the program, the method does the work and returns D0, and the program resumes. Source: `tools/headless_os.py`, docstring; `tools/headless.py`, `Headless.__init__` (the `rts` in every slot, the `_range_stop` hook), `_os_call`, `leave`; `re/notes/headless.md`, "Memory map" (`0x0C0000`–`0x0C9FFF`).
9. Why park and resume: a register written inside a Unicorn hook is lost, because the translated block carries on with its own copy; memory written inside a hook is kept. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", first point; `tools/headless.py`, the comment above `_range_stop`.
10. The stubs answer 60 library calls of six libraries: exec 26, dos 14, graphics 15, intuition 2, the devices' one (`RawKeyConvert`) and `ciaa.resource` 2. Source: `tools/headless_os.py`, the `os_` names with their aliases (`OldOpenLibrary`, `Permit`, `Disable`, `Enable`, `RemPort`, `DisownBlitter`, `BltClear`, `BltTemplate`, `RectFill`, `Draw`), counted by grep; `re/notes/headless.md`, "The stubs".
11. A call without a method ends the run with the library, the function and the call chain, so that nothing the game asks for is answered by accident. Source: `tools/headless_os.py`, docstring; `tools/headless.py`, `_os_call` (`'%s.%s is not stubbed; called from %s'`); `re/notes/headless.md`, "The stubs".
12. Files come from the disk's extracted files, `original/disk/Wings_of_Fury`, the case of a name ignored; a file the game writes goes into an overlay and nothing is ever written to `original/`. Source: `re/notes/headless.md`, "The stubs" (`dos.Lock`, `Open`; `Read`, `Write`, ...); `tools/headless_os.py` (`GAME_DIR`, `overlay`).
13. A directory is listed in the order the disk's file system hands its entries out, read from the disk image. Source: `re/notes/headless.md`, "Directories"; `tools/headless_os.py`, `adf_order`; `SPEC.md` 8, row "Whole game, logic".
14. Memory comes from a bump allocator that never reuses an address, so every address is the same in every run and fresh memory is zero. Source: `re/notes/headless.md`, "Memory map" (`0x200000`–`0x9FFFFF`, "memory is never reused, so every address is reproducible and fresh memory is zero"); `tools/headless.py`, `alloc`.
15. `AddIntServer` keeps the list of the game's VBlank servers (interrupt 5 only); the game installs two, `soundfx_vblank` (`0x01EC64`, priority 30) and `vblank_server` (`0x011754`, priority −10). Source: `re/notes/headless.md`, "The stubs" and "Scheduling"; the re-measured run (2 calls of `exec.AddIntServer`).
16. `graphics.Text` draws nothing and moves the pen on by 8 a character, as the system font topaz 8 would; what a dialog's text looks like is not observable, its pen positions are. Source: `re/notes/headless.md`, "The stubs" and "Not covered"; `tools/headless_os.py`, `os_graphics_Text` ("topaz 8 moves the pen"); `re/notes/system-font.md`, opening (the dialogs draw with `Text` in topaz 8).
17. Why stubs are enough: the game uses the operating system for its files, its memory, its display records and its key handler, and otherwise does its own work. Source: `SPEC.md` 3.4 ("The game builds its own display with graphics.library and otherwise does its own work"), and its table.
18. A stand-in has to know a few habits of the game's code; one: the fire button of port 1 is read at `0xBFE0FF`, a mirror of CIA-A's port register, which the chip answers at every odd address from `0xBFE001` to `0xBFE0FF`; with plain memory there the button reads as pressed for ever and the title sequence is skipped, so the harness writes the register to all of them. Source: `re/notes/headless.md`, "What runs and what does not" (the three habits); `tools/headless.py`, `set_ciaa_pra`.
19. Two services of the Kickstart ROM run for real: `mathffp.library`, the fast floating point the game's tick computes with, and console.device's `RawKeyConvert` with the ROM's default keymap, which turns a raw key code into a character. Source: `re/notes/headless.md`, "Game logic uses floating point" and "The keyboard needs the ROM too"; `SPEC.md` 8, row "Whole game, logic".
20. Why for real: both are pure register code that reads nothing of the machine, so the ROM's own routines can run as they are; a stand-in written for the harness would be a second implementation and could not be shown exact, while the port's own floating point is held to the ROM's (chapter 5), so the reference has to be the ROM itself; the keymap is not on the game's disk. Source: `re/notes/headless.md`, "Game logic uses floating point" ("The routines are pure register code, so the real ones run"; "The harness does not model this arithmetic") and "The keyboard needs the ROM too" ("That routine is pure ... so the real one runs from the ROM as well"); `re/notes/keys.md`, "Raw code to character: console.device" (the keymap "not on the game disk"); `re/notes/ffp.md`, "How the game reaches it"; chapter 5, "The ROM's own floating point".
21. The ROM is mapped where it lives, `0xFC0000` for a 256 KB image; both services are found in it by their names and contents, never by a fixed address (mathffp 34.1 in Kickstart 1.3). Source: `re/notes/headless.md`, "Game logic uses floating point" and "The keyboard needs the ROM too"; `re/notes/ffp.md`, "How the game reaches it"; `tools/headless.py`, `_map_rom`, `_map_rom_mathffp`, `find_rom_console`.
22. Without the ROM no run starts: the harness raises the ROM check's message where it opens the ROM. Source: `tools/headless.py`, `_map_rom` (`romcheck.read()`, `HarnessError`); `re/notes/testing.md`, "Without the Kickstart ROM".
23. The custom chips' addresses are plain memory, so nothing is drawn: the blitter and the copper do nothing, and the program's waits for the blitter fall through because the busy bit of `DMACONR` reads as 0. Source: `re/notes/headless.md`, "What runs and what does not", the table (the blitter, the copper); "Memory map" (`0xDFF000`–`0xDFFFFF`).
24. That costs the logic nothing: chapter 2 showed the game never reads back what was drawn, and the headless original holds it: display memory is a region of its own, every read of it by the processor is counted by routine and block, and over the front end without input, a take-off, 1260 ticks of flight and a crash off the deck no bitplane was read at all; the only reads were the copper builder reading its own lists and `text_render` reading the template it builds; a test fails if any other routine ever reads display memory. Source: `re/notes/headless.md`, "Read-back"; `tests/test_headless.py`, `test_no_logic_reads_what_was_drawn`; `book/docs/part-1/amiga.md`, "Nothing in the game's logic ever reads back what the blitter wrote".
25. The exceptions to plain memory: `VHPOSR` (`0xDFF006`, the beam's position, served from the entropy stream), `JOY1DAT` and CIA-A's port register (the scripted controller), Paula's audio registers (a model of the four channels and their interrupts) and CIA-A's timer A (the music's timer). Source: `re/notes/headless.md`, "Memory map" (the CIAs, the custom chips); `SPEC.md` 8, row "Whole game, logic".
26. Paula is the one chip plain memory could not stand in for: the sound effects engine learns that a sample has played from the audio interrupt, which plain memory never raises; the model watches the game's writes to the audio registers, plays the four channels in a time of its own counted between VBlanks, and calls the handler the game put at the level-4 vector; the port's Paula is the same model, so the two logs of sound samples can be held to each other. Source: `tools/headless_paula.py`, docstring; `re/notes/headless.md`, "The audio channels"; `SPEC.md` 6.5 ("The model is the one the headless original runs").
27. The model only observes where nothing sounds: a flight with the music switched off gives the same steps, schedule and random reads with the model and without it, but for the copy `soundfx_vblank` keeps of a read-back register. Source: `re/notes/headless.md`, "The audio channels" (the paragraph after the event log); `tests/test_sound.py`, `test_the_model_changes_no_step_of_a_silent_run`.
28. The music player runs for real by default: `LoadSeg` loads `songplay` and `wofsongs` from the disk as dos does, CIA-A's timer A counts in the channels' time and its underflow calls the player's own interrupt routine, and every call into either file is recorded with its registers, VBlank, pass and tick; with `"music": false` two fake segments answer every call with 0, which the game reads as idle. Source: `re/notes/headless.md`, "What runs and what does not", the table, row "The music player and the song data", and "The music's timer"; `tools/headless.py`, `DEFAULT_RUN` (`'music': True`), `_segment_call`; `re/notes/music.md`, the table of tools and "The timer"; `SPEC.md` 8, row "Whole game, logic" ("The music player runs for real since M8 part 2"). (The docstring of `tools/headless.py`, "The music player is not run; calls into it are recorded", and the test name `test_the_music_player_is_recorded_not_run` predate the real player; the test checks the record of the calls, which both modes keep.)
29. The real player changes nothing of a mission: from the mission's start on, the run with the real player and the run with the player answered as idle have the same schedule, ticks, passes, random reads and state. Source: `tests/test_music.py`, `test_the_music_changes_nothing_of_the_mission` and its docstring.
30. The crack's text screen (`0x01F41A`) is skipped, returning 1 at once, because it draws random numbers the port never draws. Source: `re/notes/headless.md`, "What runs and what does not", the table; `SPEC.md` 8, row "Whole game, logic" ("which would draw entropy the port never draws").

## Time: the program runs until it waits

32. The problem: the main program blocks in its waits and the VBlank interrupt is asynchronous; on the machine the interrupt arrives whenever the beam reaches the bottom of the picture, wherever the program is **(reference: HRM, chapter 7, interrupts)**; an emulator that delivered interrupts after some count of instructions would make every result depend on the emulator. Source: `re/notes/headless.md`, "Scheduling", first paragraph.
33. The rule: the program runs until it waits, and VBlanks happen only where it waits; nothing else about time reaches the program. Source: `re/notes/headless.md`, "Scheduling" (in bold); `tools/headless.py`, docstring.
34. The wait points, five kinds: the spins in `wait_vblank` (`0x01AA44`) and `wait_next_vblank` (`0x01AA36`) reached with `vblank_flag` clear, one VBlank, which sets the flag; `graphics.WaitTOF`, one; `dos.Delay(n)`, n × `video_hz` / 50; the entry of `frame_update` (`0x010228`), the start of a pass, as many as are still owed so that the configured number lie between this pass's start and the previous one's, at least one if the flag is clear; a round of the fade's wait in `music_start` or `music_stop`, four. Source: `re/notes/headless.md`, "Scheduling", the table; `tools/headless.py` (`SPINS`, `FRAME_UPDATE`, `_pass_begin`, `MUSIC_SPINS`, `MUSIC_SPIN_VBLANKS = 4`); `tools/headless_os.py`, `os_graphics_WaitTOF`, `os_dos_Delay`.
35. The listing `wait_vblank` (`0x01AA3E`–`0x01AA4E`, with its header): `tst.b vblank_flag` and `beq.b` back to the same test, a spin until the flag is set, then `clr.b vblank_flag`; its callers `frame_update`, `view_show_wait`, `cop_show_wait`. Source: `re/Wings.lst` `0x01AA3E`–`0x01AA4E`; `re/functions.csv` (`01aa3e`, asm).
36. The listing `vblank_server`'s first three instructions (`0x011754`–`0x01175E`): the VBlank server saves the registers, sets A4, and `st.b vblank_flag` sets the flag the spin waits for; the listing's own comment: every fourth VBlank it samples one input byte into the queue. Source: `re/Wings.lst` `0x011754`–`0x01175E` and the header's comment; `SPEC.md` 3.3.
37. The harness hooks the spin's test instruction: reached with the flag clear, it delivers one VBlank, whose server sets the flag, and the spin falls through at once. Source: `tools/headless.py`, `_spin`, `_drive` (`elif address in SPINS: ... self.deliver_vblanks(1)`).
38. A VBlank in the harness: the audio channels' and the timer's events of the VBlank that has passed are delivered, `JOY1DAT` and CIA-A's port register are set from the script, the script's keys are delivered, and every server the game installed is called, highest priority first, as a nested call on a stack of its own with the registers an interrupt server gets. Source: `re/notes/headless.md`, "Scheduling" ("A VBlank is: ..."); `tools/headless.py`, `_vblank`.
39. The original's own VBlank counters count exactly the VBlanks the harness delivers. Source: `tests/test_headless.py`, `test_the_originals_counters_count_what_the_harness_delivers`.
40. So nothing depends on instruction counts or on how fast the emulator is; work that only burns processor time between two waits, a fade's step, takes no time, and its duration is not defined in the original either. Source: `re/notes/headless.md`, "Scheduling" ("Consequences": "Fades and other CPU-bound delays take no time. Their duration is not defined in the original either"); `tools/headless.py`, docstring ("Nothing depends on instruction counts or on how fast the emulator is").
41. The number of VBlanks a pass takes is a setting of the run, `vblanks_per_pass`, 2 by default; in play a pass is two VBlanks and a pass, with a tick after every second pass. Source: `re/notes/headless.md`, "Run description" and "Scheduling", "Consequences" ("During play a pass is `V V P` with the provisional two VBlanks per pass, a tick follows every second pass"); `tools/headless.py`, `DEFAULT_RUN`.
42. The run records its schedule as it happened, `V` with the controller's state, `P` with the pass's number, `T` with the tick's input byte, `S` at a mission's start; the port's tests replay exactly that sequence through the port's entry points for a VBlank and a pass. Source: `re/notes/headless.md`, "Scheduling", "Consequences"; `tools/headless.py`, `_vblank`, `_pass_begin`, `_tick_end`, `_mission_start` (`self.schedule.append`); `SPEC.md` 8, row "Front end" (the schedule replayed through `wof_vblank`, `wof_key`, `wof_pass`).
43. Tests: every pass of a mission begins two VBlanks after the last; with the setting at 3, three; one tick for every four VBlanks. Source: `tests/test_headless.py`, `test_every_pass_of_a_mission_begins_two_vblanks_after_the_last`, `test_the_pass_period_is_a_setting`, `test_one_tick_for_every_four_vblanks`.
44. The schedule is an input of the simulation: how passes and ticks interleave decides what the game does, and the logic tick runs at a quarter of the VBlank rate while a pass runs as often as the machine manages; why two VBlanks a pass is chapter 7's. Source: `re/notes/passes.md`, "What the question is" (in bold: "So how passes and ticks interleave is an input of the simulation"); `book/BOOK.md` 3, chapter 7.
45. The fade's wait: `music_start` and `music_stop` ask the player again and again whether the song's fade has ended, a spin with no wait in it; on the machine the timer's interrupts end the fade while it spins; the harness gives each round four VBlanks, which keeps the phase of the server's count of four for the input sample, and the script waits meanwhile. Source: `re/notes/headless.md`, "The fade's wait".
46. The re-measured run (claim 70) shows the schedule after a mission's start: `S`, `V`, `P`, `T`, then `V V P` and a `T` after every second `P`. Source: the run at `0c453c5`, `m.schedule` after `('S', 1)`: `('S', 1), ('V', 0), ('P', 1), ('T', 32), ('V', 0), ('V', 0), ('P', 2), ('V', 0), ('V', 0), ('P', 3), ('T', 0), ...`. (Sheet only; the prose describes the pattern.)

## Input, VBlank by VBlank

47. The input is a script of the player's hands by VBlank: segments of a number of VBlanks, the letters `U`, `D`, `L`, `R`, `F` for the stick and the button, and optionally raw key codes delivered at the segment's first VBlank; neutral after the last. Source: `re/notes/headless.md`, "Run description" (`raw`) and "Input"; `tests/test_headless.py`, module docstring ("The scripts below are the player's hands, VBlank by VBlank; they hold no game data").
48. `U` is the stick pushed forward, bit 0 of the input byte. Source: `re/notes/headless.md`, "Input"; `tools/headless.py`, `RAW_BITS`.
49. The harness turns a VBlank's letters into hardware state, not into an input byte: `JOY1DAT` through a table it builds at the start by calling the original's own decoder `read_joy_bits` (`0x01520E`) on all 16 combinations of the register's four direction bits, and bit 7 of CIA-A's port register, active low, for the button; opposing directions cancel, as a real stick cannot give them. Source: `re/notes/headless.md`, "Input"; `tools/headless.py`, `_joy_words`, `_vblank`.
50. Why through the registers: the input byte, the tap and hold latches, the queue and the message ticker are then the original's own work, done by its VBlank routines. Source: `re/notes/headless.md`, "Input" ("The input byte, the tap and hold latches and the queue are then the work of `vblank_every_frame`, `read_joystick` and `vblank_server`"); `tools/headless.py`, docstring ("The input byte, the tap and hold latches, the queue and the ticker are therefore the original's own work").
51. Why ask the original's decoder: so that no reading of the stick's bits is assumed; the story of a reading that was wrong is chapter 9's ("the stick's bits"). Source: `tools/headless.py`, `_joy_words` ("found by asking the original's own decoder"); `book/BOOK.md` 3, chapter 9; `book/docs/part-1/reading.md` ("Chapter 9 tells of a reading of the stick's bits that the running original contradicted").
52. Tests: the tick's input is the original's own input byte (stick right bit 2, forward bit 0, a short press of fire bit 5 for exactly one tick); held, fire becomes the hold bit after ten VBlanks; the forward switch is bit 0. Source: `tests/test_headless.py`, `test_the_tick_input_is_the_originals_own_input_byte`, `test_holding_fire_becomes_the_hold_bit_after_ten_vblanks`, `test_bit_0_of_the_input_byte_is_the_forward_switch`; `re/notes/headless.md`, "Input" ("What the tests establish about the byte").
53. Keys go as raw-key events through the handler the game put on input.device (`input_handler` `0x02075A`), before the servers of that VBlank; a key may carry a qualifier, the state of keys such as Control. Source: `re/notes/headless.md`, "Input" ("**Keys** are raw Amiga key codes ..."); `tools/headless.py`, `key_event`.
54. Test: cursor down and return choose the second rank, through the game's own handler. Source: `tests/test_headless.py`, `test_a_key_goes_through_the_originals_input_handler`.
55. A second input mode, byte mode, replaces the byte the server has just sampled, the queue staying the original's. Source: `re/notes/headless.md`, "Input" ("**Byte mode**"); `tests/test_headless.py`, `test_input_bytes_can_be_given_directly`. (Sheet only, or one clause.)
56. A run is described by a JSON file: the entropy, the video rate, the VBlanks per pass, the audio model and the music, the script, byte mode, files laid over the disk, `argc`, and where to stop (after a number of ticks, passes or VBlanks); every key is optional. Source: `re/notes/headless.md`, "Run description"; `tools/headless.py`, `DEFAULT_RUN`, `load_run`.
57. The listing `flight-control-f` (`tests/runs/flight-control-f.json`): five presses of fire, each three VBlanks, thirty apart, carry the front end along; 40 VBlanks into the mission the key 35 with Control, which is Control-F, the vertical flip; then 600 neutral VBlanks; the run stops after 300 of the script's VBlanks. JSON has no hexadecimal, so the key's code is written in decimal, `35` for `0x23`. Source: `tests/runs/flight-control-f.json`; `re/notes/keys.md`, "In flight and paused" (`0x23` with Control toggles `opt_invert_vertical`) and "The run description's keys" (decimal, `[35, "ctrl"]` is the F key with Control); `re/notes/headless.md`, "Using it" (the five presses).
58. The descriptions in `tests/runs/` hold no game data, only the player's hands; there are 34. Source: `tests/test_frontend.py`, module docstring ("The run descriptions live in tests/runs/ and hold no game data: they are the player's hands"); `ls tests/runs | wc -l` at `0c453c5`.
59. With those five presses the mission begins at VBlank 444, 312 of them the three fades' waits, during which the script waits. Source: `re/notes/headless.md`, "Using it"; re-measured at `0c453c5` (claim 70).
60. A run without any input also reaches a mission: the title sequence runs out, the rank selection gives up after 1800 VBlanks of waiting and asks for the attract demo, whose file is not on the disk, and a mission begins after 7237 VBlanks. Source: `re/notes/headless.md`, "The front end runs for real"; `tests/test_headless.py`, `test_left_alone_the_program_starts_a_mission_by_itself` (`vblanks > 6900`, `('Lock', 'wofdemo', False)`).

## Chance from a stream

61. The game's one random source in use, `rand_beam` (`0x0203BE`, 42 call sites), returns a constant exclusive-ored with the beam's position at the moment of the call, so on the machine all its chance is processor timing. Source: `re/notes/random.md`, "The generator"; `SPEC.md` 3.3.
62. Every read of `0xDFF006` takes the next value of the entropy stream: a hook on the register writes it into the register's memory before the read completes. Source: `re/notes/headless.md`, "Entropy"; `tools/headless.py`, `_beam_read`.
63. The stream is the generator of the port's `src/rand.c`, a linear congruential generator whose values are shaped like the beam's register (high byte 0 to 255, low byte 0 to `0xE3`), or an explicit list, which ends the run when it is used up, or one value for ever. Source: `tools/headless.py`, `entropy_values` (`state * 1664525 + 1013904223`), `Headless.__init__` (entropy); `re/notes/headless.md`, "Entropy" and "Run description"; `SPEC.md` 7.3 (the shape); `re/notes/random.md`, "The generator" (VHPOSR's layout). The term "linear congruential" **(reference: Wikipedia, "Linear congruential generator")**.
64. A test compares the harness's generator with the native library's, 2000 values for each of five seeds. Source: `tests/test_headless.py`, `test_the_entropy_generator_is_the_ports`; `re/notes/headless.md`, "Entropy".
65. The log names, for each read, the value, the routine that called `rand_beam` or `read_vhposr`, and the VBlank, pass and tick. Source: `re/notes/headless.md`, "Entropy"; `tests/test_headless.py`, `test_the_log_of_beam_reads_names_the_callers_in_order`.
66. Why: a run can be repeated exactly, and the port, given the same stream, draws the same values as long as it calls `rand_beam` in exactly the original's order; a call out of order shows at once as a difference, which makes the stream a check of its own. Source: `re/notes/random.md`, "Consequences" ("**The headless original (milestone M2) must hook reads of `0xDFF006` and serve the same stream.** ... A divergence in call order shows up immediately as a state mismatch, which makes this an additional fidelity check"); chapter 1, "Logic, tick for tick" (the stream named there without the word).
67. Observed: on the deck nothing reads; in the air one routine in the call tree of `draw_world` reads twice in every pass, 4191 reads in 1260 ticks. Source: `re/notes/headless.md`, "Entropy" ("Observed").
68. Another stream gives other dumps from the first step on, with the same schedule. Source: `tests/test_headless.py`, `test_another_entropy_stream_gives_other_dumps` (every step's hash differs; the schedules equal); `re/notes/headless.md`, "Entropy" ("A different seed changes the state from the first dump on").

## What a run leaves

69. The dump: a record when a mission's inner loop is first reached (`S`), after every logic tick (`T`) and after every pass (`P`), each with the totals of missions, ticks, passes, VBlanks and random reads, the tick's input, a SHA-256 hash of the state, and the bytes of the state that changed since the record before. The state is the executable's DATA and BSS, `0x023000`–`0x028004`, and every live allocation outside display memory. Source: `tools/headless_dump.py`, docstring; `re/notes/headless.md`, "Dump"; `tools/headless.py`, `_step`, `regions`. SHA-256, a 32-byte digest **(reference: FIPS 180-4, 6.2)**.
70. A flight of 1260 ticks is 3778 records and 1.8 MB (the note); re-measured at `0c453c5`: 1,000 ticks after a mission's start gave 1,999 passes and 3,997 VBlanks, 3,001 records in all (1,001 `T` with the tick `main` runs itself at the mission's start, 1,999 `P`, one `S`) and a dump of 1,500,768 bytes. Source: `re/notes/headless.md`, "Dump"; the scratchpad script at `0c453c5` (`FRONT + TAKE_OFF`, `stop ticks 1001`, `run(until='inner')` then `run()`).
71. Why every record carries only the change and a hash: the state is rebuilt from the changes and checked against its hash, so a reader can trust its own reconstruction; a test rebuilds every step of a dump and checks each against its hash, and display memory is not in the dump. Source: `tools/headless_dump.py`, docstring ("so a reader can check its own reconstruction"); `tests/test_headless.py`, `test_a_dump_rebuilds_every_step_it_holds`.
72. Beside the dump a run keeps the schedule, the log of random reads, the files it opened, the music player's calls and the log of sound samples. Source: `re/notes/headless.md`, "Using it" (`schedule`, `entropy_log`, `player_calls`, `files_log`, ...) and "The audio channels" (the event log).
73. The change report hooks every write to the dumped memory and lists per record the ranges whose content changed, the old and the new bytes, a name and the routines that wrote them; a name is the address's in `re/names.txt`, or the listing's automatic name with the nearest name below it for orientation, and an address in an allocation is an offset into it named after its owner, the routine that asked for it. Source: `re/notes/headless.md`, "Change report, entropy log, schedule"; `tests/test_headless.py`, `test_the_change_report_names_who_wrote_what`.
74. A change report of a few hundred ticks is tens of thousands of lines, of a few thousand ticks tens of megabytes; the write summary keeps the whole run in a few hundred lines: every write tagged with its phase (`V` inside a VBlank, `T` inside the logic tick's tree, `F` inside the pass's tree, `M` the main program) and its routine, neighbouring addresses written the same way joined into one range. Source: `tools/headless_writes.py`, docstring; `re/notes/headless.md`, "Write summary, read hook"; `tests/test_headless.py`, `test_the_summary_says_in_which_phase_a_range_was_written`.
75. The stride detection reads a table's record size off the ranges one routine wrote: a test finds the pool of `0x14`-byte records that `player_lost_restart` clears at the mission's start. Source: `re/notes/headless.md`, "Write summary, read hook" ("**Tables.**"); `tests/test_headless.py`, `test_the_stride_detection_finds_a_table_of_records`, `test_the_stride_detection_finds_a_real_pool`; chapter 4, "A table by its stride".
76. The read hook watches chosen memory, by address or by the owner of an allocation ("the map", "the pools"), and gives per read the routine, the phase and the offset. Source: `re/notes/headless.md`, "Write summary, read hook" ("`read_owners` and `read_ranges`"); `tests/test_headless.py`, `test_the_read_hook_says_who_read_a_watched_range`.
77. Observers: a routine named or given by address is recorded at every entry with the VBlank, pass and tick, all sixteen registers and the words above the return address, which are a C routine's arguments; on request also its return with the condition codes, read by running a move from the status register inside the emulation (chapter 5), and chosen memory at both ends. Source: `re/notes/headless.md`, "Observers"; "Unicorn, as it behaves here", fourth point.
78. That is how the notes know what each front-end screen draws and what the floating point is handed in flight. Source: `re/notes/headless.md`, "Observers" ("This is how `re/notes/frontend.md` knows ..."; "how `re/notes/ffp.md` knows ..."); chapter 4.
79. Observing changes nothing: an observer and the other instruments only read, and tests hold a run with them to the same records and the same schedule as a plain run. Source: `tests/test_frontend.py`, `test_an_observer_does_not_change_a_run` and its twin for returns and memory; `tests/test_headless.py`, `test_an_instrument_does_not_change_a_run`; `re/notes/headless.md`, "Observers", "Write summary, read hook".
80. A hook added after a block was translated does not fire for it, so every hook is installed before the first instruction runs. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", second point; `tools/headless.py` (the comments "Unicorn does not re-translate for a new hook"). (Sheet only, or the dev sidebar.)

## The same run, twice

81. Two runs of one description give identical dumps, byte for byte, the same schedule and the same random reads. Source: `tests/test_headless.py`, `test_two_runs_give_identical_dumps`.
82. Another input gives dumps that agree hash for hash until the scripts part, and never after; they part within eight VBlanks of the scripts' parting. Source: `tests/test_headless.py`, `test_another_input_gives_other_dumps` (`<= vblank_of_parting + 8`).
83. Long runs on request: a flight of 1500 ticks twice, and the front end left alone twice, give the same records. Source: `tests/test_headless.py`, `test_a_long_flight_twice`, `test_left_alone_the_program_starts_a_mission_by_itself` (`WOF_SLOW_HEADLESS=1`).
84. What makes it so: the program's time is only the VBlanks of its waits, its chance only the stream, its memory addresses the same in every run, and its input the script. Source: claims 14, 33, 47, 62.

## Wall time never shapes a run

85. The emulation runs in slices of a fixed number of instructions, a million by default, between which the harness looks at the wall clock; where a slice ends is no wait point and nothing the program can notice. Source: `re/notes/headless.md`, "Scheduling" (the paragraph after the rule) and "Unicorn, as it behaves here", fifth point; `tools/headless.py`, `SLICE_INSNS = 1_000_000`, `_drive`.
86. A slice is ended by Unicorn's instruction counter, a code hook it runs ahead of every other one: a slice ends before an instruction whose own hooks have not run yet, at a place that depends on the program alone, and the next slice starts there exactly. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", fifth point; `tools/headless.py`, `_drive`, docstring.
87. Unicorn can also end an emulation after a time, a timeout, which stops it from a timer thread, asynchronously; a slice must never end that way in a run that goes on. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", sixth point; `tools/headless.py`, `_drive`, docstring; Unicorn's API **(reference: `uc_emu_start`'s `timeout`)**.
88. The first fault: Unicorn sets the program counter to the accessing instruction before it calls a memory hook, and the access follows the hook; a timeout that lands while a memory hook runs stops with that instruction reported and its access made, but not its register updates, and the next slice executes it again: a write made twice, a decrement of memory counted twice, a beam read that takes a second value. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", the first sub-point; `tools/headless.py`, `_drive`, docstring.
89. Measured on one mission script with slices of 3 ms, about 21,000 timeouts a recording: ten such recordings all differed from the unhurried one, always first by a counter one apart; one crashed on a corrupted return address and three hung. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", sixth point (`japcarrier_m`, "from steps 17 to 185 on").
90. Of 9,799 timeouts in one recording, 4,594 stopped on their slice's last memory-hook event and 4,588 of those accesses were made a second time: 179 writes of a different value, an increment counted twice and 434 beam reads that took a second value. Source: the same sub-point. (Sheet only; the prose keeps the mechanism, not the counts.)
91. With the old slices of two seconds this needed the process to stall that long, which the full suite once met: the oil timer's `subq.w #1` at `0x0113A2` ran twice, 43 against 44 from tick 692 on. Source: the same sub-point. The story of how it was found is chapter 9's ("the timeout"); the prose gives one sentence. **Marked for chapter 9.**
92. The second fault: a timeout landing between Unicorn's two stop flags left every code hook silent for the next slice, so the hook on `wait_vblank`'s spin never fired and the program spun there for ever: the hung recordings. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", the second sub-point; `tools/headless.py`, `_drive`, docstring ("Landing between Unicorn's two stop flags, it left every code hook silent for the next slice, and the program spun in `wait_vblank` for ever").
93. The cure: slices ended by the instruction counter; wall time only ever ends a run, as Stuck: no wait point for 60 s, or a whole run longer than 1,800 s. Source: `tools/headless.py`, `STUCK_SECONDS = 60.0`, `WALL_LIMIT = 1800.0`, `Stuck`, `_drive`; `re/notes/headless.md`, "Unicorn, as it behaves here", fifth point; `re/notes/testing.md`, "The wall-clock limits of the headless original".
94. Why those limits: measured under the suite's parallel phase, the longest stretch between two wait points was about 8 s with the machine idle and about 10 s with the owner at the machine, the longest whole run 327 s idle and 701 s busy; the limits were 10 s and 600 s, and with 12 workers a recording reached 600 s and its two tests failed as Stuck; so the limits are sized for a loaded machine. Source: `re/notes/testing.md`, "The wall-clock limits of the headless original", the table and the paragraph after it; `tools/headless.py`, the comments at `STUCK_SECONDS`, `WALL_LIMIT`.
95. The test `test_where_a_slice_ends_changes_nothing`: three flights with every kind of hook in use, in slices of 97 instructions (an odd length, so that the ends fall everywhere), of the default length and of 10^10 (one slice from each wait point to the next), give the same records, the same random reads, the same schedule and the same observed calls; the short slices end more than 10,000 times, the longest never. Source: `tests/test_headless.py`, the test and its docstring.
96. The test `test_wall_time_only_ever_ends_a_run_as_stuck`: with the limit at nothing, the first slice that ends without a wait point makes the run Stuck. Source: `tests/test_headless.py`, the test.
97. With the counter every code hook fires once per execution of its instruction, so an observer keeps every call it sees; a guard against a hook firing twice is gone. Source: `re/notes/headless.md`, "Unicorn, as it behaves here", fifth point and the paragraph after the sub-points. (Sheet only, or one clause.)
98. The counter costs nothing measurable: the same mission recorded in 38 s with it and in 40 s with the timeout it replaced. Source: `re/notes/headless.md`, "Speed".
