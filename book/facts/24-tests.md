Every claim the chapter makes, one line each, with its source, in the order of the chapter. A claim without a source goes to the list at the end and stays out of the draft. The chapter calls them "the release's run", without a date. The times of the older runs are `re/notes/testing.md`'s, measured when the suite was smaller.

Words used in the sheet as the chapter will use them, each in one sense. **The suite** is the repository's tests under `tests/`, run by pytest. **A run of the suite** is one invocation of pytest over it, whole or in a phase; "a run" alone is not used for it. **A phase** is one of the two parts the suite is run in; the reach map's phases of chapters 7 and 8 (a VBlank server, the tick, the pass, the main program) are "the harness's phases" where they must be named, and the chapter does not need them. **A test process** is one of the processes pytest-xdist starts, which pytest-xdist and the code call workers; "worker" stays chapter 10's session. **A processor core** is the machine's; "the core" alone is the port's. **A recording** is a mission script run once under the headless original with everything the loops compare, which the port's loops replay; the demo the port recorded is "the demo the port recorded" or "the stored replay". **A layer** is a group of the suite's tests that holds the port at one scale against one reference. **The state** is the core's. **A control** is chapter 8's, a deliberate change that a test must catch.

The reference works, each fetched once:

- pytest's documentation, start page, `https://docs.pytest.org/en/stable/`: "The pytest framework makes it easy to write small, readable tests, and can scale to support complex functional testing for applications and libraries." **(reference)**
- pytest's documentation, "How to mark test functions with attributes", `https://docs.pytest.org/en/stable/how-to/mark.html`: a mark sets metadata on a test function, for plugins and the command line; markers are registered in the configuration or programmatically in a `pytest_configure` hook; `-m` selects tests by marker, e.g. `-m "not slow"`. Elsewhere line of Marker. **(reference)**
- pytest's documentation, "Managing pytest's output", JUnitXML, `https://docs.pytest.org/en/stable/how-to/output.html`: `--junit-xml=path` writes a result file in XML that continuous-integration servers read (the repository writes the option `--junitxml`, its other spelling). Elsewhere line of Outcome set. **(reference)**
- pytest-xdist's documentation, "Running tests across multiple CPUs", `https://pytest-xdist.readthedocs.io/en/stable/distribution.html`: `-n 8` gives the number of processes; `--dist load` sends pending tests to any available worker, without any guaranteed order; `--dist loadgroup` groups tests by the `xdist_group` mark and distributes groups to workers as whole units, which "guarantees that all tests with same `xdist_group` name run in the same worker"; the workers are processes beside the main process. Elsewhere line of Test process. **(reference)**
- The Chrome DevTools Protocol, `https://chromedevtools.github.io/devtools-protocol/`: a JSON-based protocol that "allows tools to instrument, inspect, debug, and profile Chromium, Chrome, and other Blink-based browsers"; it "is not a public or supported API for Chrome, and it does not guarantee backwards compatibility". **(reference)**; the second half for "What is fragile".
- W3C, *WebDriver BiDi*, `https://w3c.github.io/webdriver-bidi/`: "a mechanism for remote control of user agents"; "Message transport is provided using the WebSocket protocol." **(reference)**
- Python's documentation, "ctypes", `https://docs.python.org/3/library/ctypes.html`: a foreign function library that "allows calling functions in DLLs or shared libraries"; a function's argument types are set by `argtypes` and its return type by `restype`, by default C's `int`. **(reference)**
- Node's documentation, "Global objects", `WebSocket`, `https://nodejs.org/api/globals.html`: a browser-compatible WebSocket, added in v21.0.0, no longer behind a flag since v22.0.0, no longer experimental since v22.4.0 (the machine's Node is v26.0.0, `node --version`). **(reference)**
- Python's documentation, "fcntl", `https://docs.python.org/3/library/fcntl.html`: `LOCK_EX`, "Acquire an exclusive lock." **(reference)**
- Martin Fowler, "Eradicating Non-Determinism in Tests", `https://martinfowler.com/articles/nonDeterminism.html` (chapter 9's further reading): a test that leaves data behind "can corrupt the run of another test"; the remedies, "always rebuild your starting state from scratch, or ensure that each test cleans up properly after itself". Elsewhere line of Fresh core. **(reference)**

## The generator

`book/tools/suite.py` (new) runs `.venv/bin/python -m pytest tests/ --collect-only -q` from the repository, counts the tests of each module, groups the modules by the layers of `book/suite.toml` (new: the layers in order, each with its name and its modules) and writes `docs/generated/tables/suite-layers.md`, a Markdown table that the chapter includes with a snippet. It fails (exit 2) when a test module under `tests/` is in no layer or in two, or a layer names a module that has no tests, so that a new module cannot slip out of the table. `book/tools/build.py` runs it as a step of its own, `suite`, and `--check` makes it again into a temporary directory and compares. It needs only the repository and pytest, no ROM and no native library (the collection skips nothing out); it runs in about a second. `mkdocs.yml` excludes `generated/tables/` from the site's pages (`exclude_docs`), so that the table is no page of its own, and its comment on the snippets names the tables beside the listings.
