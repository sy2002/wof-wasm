## The arrangement

7. The oracle: one original routine taken at its address in the listing, run on an emulated 68000 with the executable mapped at the fixed layout, beside its port compiled for the test machine, on the same inputs; the results must be equal. Source: `tools/oracle.py`, docstring; `SPEC.md` 4, "The oracle"; `SPEC.md` 7.4, step 4; the glossary's entry Oracle (chapter 1).
8. A test that runs two implementations of the same thing on the same input and compares the outputs is a differential test; the project's tests call themselves so. Source: `tests/test_oracle_m1.py`, docstring ("Differential tests for the routines M1 ports"); `tests/test_oracle_m3.py` to `m8.py`, docstrings ("differential tests"); Wikipedia, "Differential testing", fetched once (Elsewhere link).
9. The emulator is Unicorn Engine, a CPU emulator that reuses the CPU emulation of QEMU and lets a program register handlers for events from an instruction's execution to a memory access; it emulates the m68k. Source: Unicorn Engine's site **(reference)**; `requirements.txt` (`unicorn==2.1.4`); `SPEC.md` 2 (`unicorn` 2.1.4, "68000 emulation").
10. Unicorn's m68k starts as a ColdFire core, which lacks `DBcc` and other 68000 instructions; the oracle sets the model to the 68000. Source: `tools/oracle.py`, `Oracle.__init__` (the comment and `ctl_set_cpu_model(UC_CPU_M68K_M68000)`).
11. The emulated machine has 2 MB of flat memory from address 0; the executable is loaded by `tools/hunk.py` at the fixed layout, code at `0x010000`, its relocations applied, so every address of the listing can be called. Source: `tools/oracle.py` (`RAM_BASE, RAM_SIZE = 0x000000, 0x200000`, `hunk.load(exe)`, the segments written at their bases; the docstring "every address in re/Wings.lst can be called directly"); `tools/hunk.py`, `load` (bases from `0x10000`, each hunk at the next 4 KB boundary; reloc32 applied); chapter 3 (the fixed load layout, relocations).
12. The port's side: the same C sources compiled by the test machine's own compiler into a library, `tests/libwofcore.dylib`, which the tests load directly and call; the page runs the same sources compiled to WebAssembly. Source: `SPEC.md` 5 (the second target, natively with Apple clang, "for the tests") and 6.1 ("The same sources must compile for `wasm32-freestanding` and natively"); `tests/conftest.py`, `Ported` (`ctypes.CDLL`); `SPEC.md` 8, row "Routine" ("against the native library").
13. Test-only entry points reach the ported routines and the loaded containers through plain numbers, compiled into the test library and into nothing else. Source: `tests/shim.c`, header comment ("Compiled into tests/libwofcore.dylib and into nothing else: dist/core.wasm never sees it").
14. The figure `oracle.svg`: the routine from the listing in the emulator on the left, the port's routine in the native library on the right, the same inputs into both, the outputs compared, equal or the test fails. Source: claims 7 to 13; under "Figures".

## Calling a routine without its program

15. A compiled routine is called as its callers call it, by the compiler's convention of chapter 3: the arguments pushed onto the stack, the last first, two bytes for an int, four for a long or a pointer; the result in D0. The test builds an argument with `W()` for an int and `L()` for a long or a pointer. Source: `tools/oracle.py`, docstring and `W`, `L`, `call` (the arguments joined in the prototype's order and written below the stack top, so the first lies nearest the return address); `SPEC.md` 4, "The oracle"; chapter 3 (the calling convention).
16. The return address the oracle pushes is a trap address, `0x0FFF00`, at which the emulation stops; a routine that has not reached it within its instruction budget (50 million) fails the call. Source: `tools/oracle.py` (`RETURN_TRAP = 0x0FFF00`, `emu_start(addr, RETURN_TRAP, count=max_insns)`, `max_insns=50_000_000`, "did not return ... instruction budget exhausted?").
17. An access to memory outside the 2 MB fails the call with the address and the instruction that made it. Source: `tools/oracle.py`, `_unmapped` and `call` (`RuntimeError(self.fault ...)`).
18. A4 is set to `0x02AFFE` when the routine reaches the program's variables, as the game's own code keeps it. Source: `tools/oracle.py`, `call` (`if self.a4 is not None`); `SPEC.md` 4 ("Pass `a4=0x02AFFE` when the routine touches globals"); `tests/original.py` (`A4 = 0x02AFFE`, `Oracle(a4=a4)`); chapter 3 (the small-data base).
19. A hand-written routine has no convention but its own; the test sets its registers by hand, as the routine was read: `text_width` takes the text's address in A0 and its length less one in D0. Source: `tools/oracle.py`, `call` (`regs`, "e.g. {'d0': 1, 'a0': ptr} for asm routines"); `tests/original.py`, `text_width` (`regs={'a0': string, 'd0': len(text) - 1}`); chapter 4.
20. Test buffers come from a bump allocator from `0x100000`, above the stack and the program. Source: `tools/oracle.py` (`HEAP_BASE = 0x100000`, `STACK_TOP = 0x0FF000`, `alloc`).
21. A stub is a stand-in that answers for something a routine calls but that is not under test. The first tests need three: the allocator wrapper `mem_alloc_asm` (`0x0158EC`) hands back a fixed buffer, since it wraps exec's `AllocMem`, which means nothing without the operating system; `vport_clear_planes` (`0x01A74C`), which is graphics' `BltClear`, returns at once and the test clears the same bytes itself; the call of `load_file_public` inside `font_load` becomes "D0 is the font", because the font is already in emulated memory and dos.library is not. "Nothing else is patched, and no routine under test is touched." Source: `tests/original.py`, docstring and `stub_allocator`, `stub_clear_planes`, `stub_font_loader`; `re/notes/porting-m1.md`, "How the tests establish it"; Wikipedia, "Test stub", fetched once (Elsewhere link).
22. Later tests stub a few more on the same rule, each named with its reason: exec's `Disable` and `Enable` and graphics' `WaitTOF` around the key buffer, and the copper builder and its install around the fades, which the port replaces. Source: `tests/original.py`, `stub_key_os` and `stub_copper` (docstrings).
23. The routines that read or write the game's variables run on a state the test writes on both sides: the registry of the port's globals, each with its original address, lets the harness copy a state between the oracle and the port with the byte order turned round, and the test compares every registered global and table the two touched. Source: `SPEC.md` 7.2, last point (`src/globals.def`, "copy state between oracle and port with byte-order conversion"); `tests/test_oracle_m5.py` to `m7.py`, docstrings ("every registered global and table the two touched is compared"); the glossary's entries Big-endian and Little-endian (chapter 3).

## What verified means

38. The status `verified` (chapter 4): ported and held to the original by a test of its own; for a pure routine that test is the oracle, and it is due before the routine counts as verified. Source: `CLAUDE.md`, Rules ("Pure routines get an oracle test before they count as `verified`"); `SPEC.md` 7.4, step 4 ("This is mandatory for pure routines") and step 5; chapter 4's status table.
39. A pure routine in the specification's sense: arithmetic, table lookups, decoders, collision tests, state machines over plain structures. Source: `SPEC.md` 7.4, step 4.
40. About a quarter of the 616 routines are verified (167 at `25a19a6`, sheet only). Source: `re/functions.csv` at `25a19a6` with `csv.DictReader` (verified 167, ported 155, partial 1, replace 47, drop 31, todo 215).
41. The status is kept by hand; no test and no tool but the disassembler, which carries it over, reads it; the evidence is the tests. Source: `SPEC.md` 7.4, last paragraph; `grep` over `tools/*.py` and `tests/*.py` (only `tools/disasm.py` reads the status column of `re/functions.csv`; the others that open the file read names and addresses).
42. What verified does not say: the oracle holds a routine on the inputs its test hands it, not that the port calls it at the right moment with the right state; that is held by the comparisons of whole runs, chapter 8, which also hold the routines that read or draw the world. Source: `SPEC.md` 8 (the rows "Routine" and "Mission, pass by pass"); `re/notes/porting-m4.md`, "How the port is held to the original"; chapter 4 (`ported` names another instrument).
43. An oracle test is as good as its inputs: a register's upper word was once assumed zero at a routine's entry because the recorded runs had always found it so, until a closed-loop run found it not (chapter 9 tells it); since then the rule is never to assume it, and the oracle tests of the later routines draw it at random. Source: `SPEC.md` 7.1 ("Never assume a register's upper word is 0 at an entry because the scripts so far found it so; the oracle tests draw it at random"); `re/notes/porting-m7.md`, "The port" (D1's upper word, `save_a`, pass 1,851); `tests/test_oracle_m5.py` (`test_a_dug_out_refilled_matches_the_original`, `d1 = rng.randrange(1 << 32)`), `tests/test_oracle_m6.py` (`test_a_ships_gun_shelling_matches_the_original`, D1 and D2 at random; `test_the_ships_guns_match_the_original`, the upper word chosen), `tests/test_oracle_m8.py` (D0 to D4 at random); `book/BOOK.md` 3, chapter 9. ## The instrument is checked too

44. Running `tools/oracle.py` directly is its self-test: the original's unpacker on all ten packed files against `tools/rpck.py`; it must print PASSED. Source: `tools/oracle.py`, `__main__`; `CLAUDE.md`, Commands ("must print PASSED"); `SPEC.md` 4, "The oracle"; run at `25a19a6`: ten lines "identical", "ORACLE SELF-TEST PASSED", 0.2 s.
45. The suite holds over 300 oracle tests (310 at `25a19a6` in eight files, sheet only). Source: `pytest --collect-only -q --slow tests/test_oracle*.py` (claim of "Counts").
46. An arithmetic shift right moves every bit down one place and copies the sign bit into the top, so a negative number stays negative and is halved, rounded down; a logical shift right shifts in a zero. Source: PRM 4, `ASR` and `LSR` **(reference)**; `tools/m68k_fix.py`, `asr_word` (`(value >> 1) | (value & 0x8000)`).
47. A memory-form shift is a shift instruction whose operand is a word in memory rather than a register; it moves one bit. Source: PRM 4, `ASL`/`ASR` and `LSL`/`LSR`, "Memory Shifts" **(reference)**; `tools/m68k_fix.py`, docstring.
48. The finding: the oracle test of `object_step` over random states failed because the original under the emulator bounced a bomb on an airfield into a vertical speed of `+9` where it should have gone `-2`; the port was right. Source: `re/notes/porting-m5.md`, "The emulator's memory-form shift (observed)"; `tools/m68k_fix.py` (`ARITHMETIC_SHIFTS`, the comment at `0x010BB8`: a bomb's vertical speed bouncing on a runway). Marked for chapter 9, which lists the shift among the mistakes.
49. The bounce in the listing (`object_step`, hand-written, `0x010BA4`–`0x010BEC`): the vertical speed at `+$12` of the record is negated (`neg.l`) and its upper word halved (`asr.w $12(a2)`, `0x010BB8`); at 9 or more it is capped at 9 (`cmpi.w #$9`, `blt`, `move.w #$9`); if it came to zero the object stops (`clr.b $20(a2)`); then the horizontal speed's word at `+$e` is halved (`asr.w $e(a2)`, `0x010BE0`) and `bne` branches on the result. Source: `re/Wings.lst` `0x010BA4`–`0x010BEC`; `re/functions.csv` (`object_step`, `010aa6`, asm); `tools/m68k_fix.py` (the two comments: vertical, horizontal speed).
50. A 68000 shifts the word `0xFFFD` (−3) to `0xFFFE` (−2); the emulator to `0x7FFE` (32,766), which the routine then caps at 9. Source: `tools/m68k_fix.py`, docstring ("A 68000 shifts `asr.w $12(a2)` of 0xFFFD to 0xFFFE, Unicorn to 0x7FFE"); `re/notes/headless.md`, "Unicorn, as it behaves here"; computed (`0x7FFE` is 32,766, at least 9).
51. Why: Unicorn 2.1.4 (its QEMU m68k translator) decides whether a memory-form shift is arithmetic or logical from bit 3 of the opcode, which in the memory form belongs to the field that says where the operand lies (the effective address's mode), instead of from the shift's type field (bits 10 and 9); so `asr.w d16(An)` runs as a logical shift and `lsr.w (An)` as an arithmetic one; the register forms are right. Source: `tools/m68k_fix.py`, docstring; `SPEC.md` 8, row "Whole game, logic"; `re/notes/porting-m5.md`, "The emulator's memory-form shift".
52. In the register form bit 3 is the low bit of the type (`asr.w #$1, d4` is `0xE244`, `lsr.w #$1, d2` is `0xE24A`: bits 4 and 3 are 00 and 01); in the memory form the type is in bits 11 to 9 (`asr.w $12(a2)` is `0xE0EA`: 000, then the direction 0, the 11 that marks the memory form, the mode 101 and the register 010) and bit 3 is the mode's low bit, 1 for an address register with an offset. Source: PRM 4, the instruction formats of `ASL`/`ASR`, `LSL`/`LSR` **(reference)**; `re/Wings.lst` `0x010906` (`e244 asr.w #$1, d4`), `0x010326` (`e24a lsr.w #$1, d2`), `0x010BB8` (`e0ea0012`); decoded with Capstone in the scratchpad.
53. The survey: the executable has 48 memory-form shifts: three `asr.w d16(An)` (`0x010BB8`, `0x010BE0` in `object_step`, `0x019D5E` in `cop_vport_planes`), which the emulator gets wrong; one `lsr.w d16(A4)` (`0x021586`), right by the same fault; two `asl.w d16(A5)` (`0x019E7A`, `0x019E7E`), right in result and wrong only in the overflow flag, which the next instructions overwrite before anything reads it; and 42 `roxl.w -(A0)` of the ticker's scroll (`0x01186C`–`0x0118BE`), right in result and flags. Source: `re/notes/porting-m5.md`, "The emulator's memory-form shift" ("observed with raw Unicorn"); `grep` over `re/Wings.lst` for a shift or rotate with one memory operand (48 lines: 3, 42, 2, 1).
54. The third, in `cop_vport_planes` (`0x019D18`, compiled C), halves a word argument of the routine; the port does the copper lists its own way (`replace`), so it matters to the headless original, which runs that routine. Source: `tools/m68k_fix.py`, the comment at `0x019D5E` (a word argument of the C routine); `re/Wings.lst` `0x019D58`–`0x019D5E` (`tst.w -$1c(a5)`, `beq.b`, `asr.w $10(a5)`); `re/functions.csv` (`cop_vport_planes`, C, `replace`); `SPEC.md` 6.6; chapter 6 for the headless original.
55. A hook is a routine of the test's own that the emulator calls when the program reaches a chosen instruction or touches chosen memory. Source: Unicorn's "Beyond QEMU" **(reference)**; `tools/oracle.py` (`UC_HOOK_MEM_UNMAPPED`); `tools/m68k_fix.py`, `install` (`UC_HOOK_CODE`, `begin=address, end=address`); Wikipedia, "Hooking", fetched once (Elsewhere link).
56. The correction, `tools/m68k_fix.py`: a code hook on each of the three addresses reads the address register and the instruction's offset, shifts the word as the 68000 does, writes it back, sets the condition codes X N Z V C as the 68000 would, and moves the program counter past the instruction, so the emulator never executes it. Source: `tools/m68k_fix.py`, `asr_word`, `_shift`, `install`.
57. The flags matter: the branch after the second shift reads them. Source: `re/Wings.lst` `0x010BE0`–`0x010BE4` (`asr.w $e(a2)`, `bne.w $10cca`); `tests/test_headless.py`, `test_the_memory_form_asr_is_corrected_where_the_emulator_gets_it_wrong` (the `bne` after the corrected shift, whatever the flags before).
58. The oracle installs the hook whenever it loads the game's program, and the headless original runs on the oracle, so both instruments carry the correction. Source: `tools/oracle.py`, `Oracle.__init__` (`if exe == EXE: m68k_fix.install(self.uc)`); `tools/headless.py` (`self.o = Oracle(a4=A4)`, line 309); `re/notes/headless.md`, "Unicorn, as it behaves here"; `SPEC.md` 8.
59. A test holds the fault, the correction and the list: it first demands that the emulator still shifts wrongly ("the emulator is fixed: drop the correction"), then that the corrected shift gives the 68000's word and flags for six values, that the flags reach the next branch, and that the hook's list is every `asr.w` with an address register in the listing. Source: `tests/test_headless.py`, `test_the_memory_form_asr_is_corrected_where_the_emulator_gets_it_wrong`.
60. No recorded run reaches the bounce, and the tests of M4 and M5 passed with the correction as without it: only the oracle, with its random states, could find it. Source: `re/notes/porting-m5.md`, "The emulator's memory-form shift" ("No script reaches the bounce, and the tests of M4 and M5 pass with the correction as they did without it").
61. The listings of the hook: `asr_word` and `_shift` of `tools/m68k_fix.py`. Source: the file, lines 25 to 41.
62. The condition codes are five bits the 68000 sets after most instructions, X (extend), N (negative), Z (zero), V (overflow) and C (carry), kept in the low byte of the status register; a conditional branch reads them. Source: PRM 1.1 and 3.1 **(reference)**; `tools/oracle.py` (`CCR_BITS`); `SPEC.md` 7.1 ("A branch reads the flags of the last instruction that set them").
63. The condition codes a routine leaves are part of what it does: the code after a call can branch on them. In this program five places branch on what a floating-point routine leaves, all inside the C library's number formatter, which the game never enters; the port's floating point keeps them all the same. Source: `tools/oracle.py`, the comment above `CCR_TRAMPOLINE` ("The condition codes a routine leaves are behaviour"); `re/notes/ffp.md`, "How the game reaches it" (the five sites, none of the fifteen the game reaches) and "`format_float` `0x021A40` is dead"; `SPEC.md` 7.1 (the `_cc` forms).
64. Unicorn keeps the condition codes lazily, and reading the status register from outside hands back whatever was last worked out: `addq.w #1` on `0x7FFF` reports N without V, and `tst.w` on `0x00010000` reports nothing at all. Source: `tools/oracle.py`, the comment above `CCR_TRAMPOLINE`; `re/notes/headless.md`, "Unicorn, as it behaves here"; `SPEC.md` 4, "The oracle".
65. The oracle's answer: with `ccr=True` the routine returns through two instructions of the oracle's own, a move from the status register into a memory slot and a jump to the trap address, neither of which changes a flag; the move runs inside the emulation and forces the flags to be worked out. Source: `tools/oracle.py` (`CCR_TRAMPOLINE = struct.pack('>HLHL', 0x40F9, CCR_SLOT, 0x4EF9, RETURN_TRAP)`, the comment); PRM 6, `MOVE from SR`, and 4, `JMP`: condition codes not affected **(reference)**.
66. The instrument is tested before what it measures: nine short hand-assembled sequences whose flags the 68000's manual fixes, run through the oracle; if it still read the lazy register, all but the last would come out wrong. Source: `tests/test_oracle_ffp.py`, the comment above `CONTROL` and `test_the_oracle_reports_the_68000s_condition_codes` (nine parametrised cases).

## The floating point

67. The game's flight model computes in fast floating point, whose routines are in the Kickstart ROM; six of the nine operations are used in the tick. Source: the glossary's entry Fast floating point (chapter 1); `re/notes/ffp.md`, opening; `SPEC.md` 3.4; chapter 14 for what the game computes.
68. The ROM's own routines run under the oracle: the owner's `original/kick.rom` is mapped, `mathffp.library` found by its name, never by an address, and the game's own glue called with the library's base preset to a jump table into the ROM. Source: `tests/ffp.py`, docstring; `re/notes/ffp.md`, "How the game reaches it"; `re/notes/headless.md`, "Game logic uses floating point"; `tests/test_oracle_ffp.py`, `test_the_reference_needs_no_hard_coded_rom_address`.
69. The port's nine operations, `src/ffp.c`, are mathffp 34.1's own 68000 code transliterated instruction for instruction, because a browser's floating point rounds otherwise and the game's state would drift. Source: `re/notes/ffp.md`, "The port"; `SPEC.md` 7.1 ("Never substitute `float` or `double`").
70. Compared: the whole 32-bit result, the second register and the condition codes; over a corpus of named edges, random operands shaped to make the hard cases frequent (close exponents, the last bits of the mantissa, the ends of the range, both zero divides), and every operand pair the game was seen to hand the library in the headless original. Source: `tests/test_oracle_ffp.py`, docstring, `random_cases`, `observed_cases`, `build_corpus`; `re/notes/ffp.md`, "How it is tested".
71. The corpus holds 27,194 cases at `25a19a6` (73 edges, 2,500 random per operation, the observed pairs); the prose says over 27,000. The note's "about 22,500" counts without the observed pairs. Source: `build_corpus()` counted in the scratchpad; `RANDOM_PER_OPERATION = 2500`; `re/notes/ffp.md`, "How it is tested".
72. The corpus runs through three builds of the same file: the native library, a WebAssembly module run in Node, and a native build under the undefined-behaviour sanitizer. Source: `tests/test_oracle_ffp.py`, `test_the_native_port_answers_what_the_rom_answers`, `test_the_webassembly_build_answers_the_same`, `test_the_same_code_under_the_undefined_behaviour_sanitizer`; `re/notes/ffp.md`, "How it is tested".
73. Beside the suite, `tools/ffp_soak.py` runs a million random operands per operation against the ROM, outside the suite because it takes minutes; at `25a19a6` it passed: nine operations, no difference, the divisions' traps the original's. Source: `tools/ffp_soak.py`, docstring; `SPEC.md` 4, the tools' table; run on the machine at `25a19a6` (output under "Counts").
74. Where the original divides by zero inside `SPDiv`, the 68000 takes its zero-divide exception; the port reports the same trap, and the tests compare it. Source: `re/notes/ffp.md`, "What each operation does at its edges"; `SPEC.md` 7.1; `tests/test_oracle_ffp.py`, `test_a_divisor_whose_exponent_byte_is_zero_traps`.
