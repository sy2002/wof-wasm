## Why one routine at a time

2. The port is written routine by routine from the listing (chapter 4); each ported routine names its original's address. Source: `SPEC.md` 7.4, steps 1 to 3; `CLAUDE.md`, Rules (the `orig` comment); chapter 4.
3. The comparison of whole runs of the game (chapter 8) says that the port and the original part company, from which tick on and, with a report it can make on request, which routine wrote which address; which input made it go wrong it cannot say. It is "what finally says whether the game behaves the same" (the review's B19, a softened judgement, resting on `SPEC.md` 8, the rows for the whole game, a mission and the replays). Source: `SPEC.md` 8, row "Whole game, logic" ("on request a report of which routine wrote which address in each step") and row "Mission, pass by pass" (the open loop: "a difference names its pass"); `re/notes/porting-m4.md`, "How the port is held to the original"; `book/BOOK.md` 3, chapter 8.
4. One routine run alone on inputs the test chooses says which routine and which input. Source: `SPEC.md` 7.4, step 4; `SPEC.md` 8, row "Routine"; the failure messages of `tests/test_oracle_m1.py` (`'step %d, %03X -> %03X: %04X, want %04X'`, `'case %d'`).
5. The oracle reaches inputs no recorded run reaches. A bomb kills the running soldiers within a band of pixels around where it lands, its killing span (a soldier within `x - w` to `x + w` starts dying). When the port was broken on purpose by making that span one pixel wider, the closed loop of the scripts run against it (`bomb_b`, `island_a`) went through unchanged, because no script puts a running soldier at the edge of a span; the oracle test over random states failed (a torpedo within the wider span, case 461). Source: `re/notes/porting-m5.md`, "The tick: the guns' bullets, the timers, the balloons, the engine" (soldiers hit: "a running soldier within `x - w` to `x + w` starts dying") and "How the port is held to the original", last paragraph (the controls the closed loop does not catch: "a bomb's span one pixel wider (`0x11`, `bomb_b` and `island_a` run through unchanged)"; `test_the_objects_step_matches_the_original`, case 461). The controls are chapter 8's; the prose names them in one sentence.
6. The loaders and decoders were held to the original before the original could be run whole: M1 (the file system, `load_file` with Rpck, the shape tables, the picture reader, the palettes, the font) is accepted when the decoders pass oracle tests; the headless original is M2. Source: `SPEC.md` 9, the table (M1 "decoders pass oracle tests"; M2 "Headless original"); `re/notes/porting-m1.md`, "Summary".

## The arrangement

7. The instrument that runs the original's side is the oracle (`tools/oracle.py`: one original routine at its address in the listing, on an emulated 68000 with the executable at the fixed layout); the test calls both sides, the original through the oracle and the port through `ctypes`, and compares. Source: `tools/oracle.py`, docstring; `tests/conftest.py`, `Ported` (the port through `ctypes`); `tests/test_oracle_m1.py` (`Original()` against `ported`); `SPEC.md` 4, "The oracle"; `SPEC.md` 7.4, step 4; the glossary's entry Oracle (chapter 1); the review's B15.
8. A differential test is one that hands two implementations of the same thing the same input and demands the same output; the project's tests call themselves so. Source: `tests/test_oracle_m1.py`, docstring ("Differential tests for the routines M1 ports"); `tests/test_oracle_m3.py` to `m8.py`, docstrings ("differential tests"); Wikipedia, "Differential testing", fetched once (Elsewhere link).
9. The emulator is Unicorn Engine, a CPU emulator that reuses the CPU emulation of QEMU and lets a program register handlers for events from an instruction's execution to a memory access (the prose: "watch and step in at any instruction or access to memory"); it emulates the m68k. Source: Unicorn Engine's site **(reference)**; `requirements.txt` (`unicorn==2.1.4`); `SPEC.md` 2 (`unicorn` 2.1.4, "68000 emulation").
9a. Why a library like Unicorn and not an emulator of the whole Amiga, the project's reason: an emulator of a whole machine runs the whole machine, while the tests need to call one routine, set its memory and registers and watch any instruction, thousands of times in one test, from Python. Source: the design as `tools/oracle.py` embodies it (`call` with `regs`, `alloc`, `write`, the hooks); the tests' loops (claim 35); Unicorn's "Beyond QEMU" (handlers for events from execution to memory access) **(reference)**; the review's C10.
10. Left to itself Unicorn's m68k imitates a ColdFire core, which lacks `DBcc` and other 68000 instructions; the game uses `dbra` (chapter 4, `map_load`); the oracle sets the model to the 68000. The prose calls the ColdFire "a related chip" and no more. Source: `tools/oracle.py`, `Oracle.__init__` (the comment and `ctl_set_cpu_model(UC_CPU_M68K_M68000)`); `re/Wings.lst` (115 lines with `dbra`, among them `map_load`'s).
11. The emulated machine has 2 MB of flat memory from address 0, room for the program (code from `0x010000`, the BSS from `0x028000`), a stack (top `0x0FF000`) and the test's buffers (from `0x100000`); the executable is loaded by `tools/hunk.py` at the fixed layout, code at `0x010000`, its relocations applied, so every address of the listing can be called. Source: `tools/oracle.py` (`RAM_BASE, RAM_SIZE = 0x000000, 0x200000`, `hunk.load(exe)`, the segments written at their bases; the docstring "every address in re/Wings.lst can be called directly"); `tools/hunk.py`, `load` (bases from `0x10000`, each hunk at the next 4 KB boundary; reloc32 applied); chapter 3 (the fixed load layout, relocations).
12. The port's side: the same C sources compiled by the test machine's own compiler into a library, the native library, which a test in Python loads and calls directly, routine by routine; the page runs the same sources compiled to WebAssembly, and the replay of chapter 1 holds that WebAssembly to the same results (why the native library: a Python test can call it directly). Source: `SPEC.md` 5 (the second target, natively with Apple clang, "for the tests") and 6.1 ("The same sources must compile for `wasm32-freestanding` and natively"); `tests/conftest.py`, `Ported` (`ctypes.CDLL`); `SPEC.md` 8, rows "Routine" ("against the native library") and "Whole game, replays" (native and Node's WebAssembly against stored hashes); chapter 1 ("The replay").
13. Entry points for the tests alone (over a hundred; the prose gives no count) reach the port's internals through plain numbers, compiled into the test library and into nothing else, so that a test need not mirror the port's structures and the page carries none of them. Source: `tests/shim.c`, header comment ("Compiled into tests/libwofcore.dylib and into nothing else: dist/core.wasm never sees it"; "mirroring C structs in ctypes would tie the tests to a layout that is free to change. Every entry point here is a plain scalar interface instead"; "Nothing in src/ may call any of this"); the review's B2 (128 exported; 133 lines of `wt_` definitions by a loose grep).
14. The figure `oracle.svg`: the routine from the listing in the emulator on the left, the port's routine in the native library on the right, the same inputs into both, the outputs compared, equal or the test fails. Source: claims 7 to 13; under "Figures".

## Calling a routine without its program

15. A compiled routine is called as its callers call it, by the compiler's convention of chapter 3: the arguments pushed onto the stack, the last first, two bytes for an int, four for a long or a pointer; the result in D0. The test builds an argument with `W()` for an int and `L()` for a long or a pointer. Source: `tools/oracle.py`, docstring and `W`, `L`, `call` (the arguments joined in the prototype's order and written below the stack top, so the first lies nearest the return address); `SPEC.md` 4, "The oracle"; chapter 3 (the calling convention).
16. The return address the oracle pushes is a trap address, `0x0FFF00`, at which the emulation stops; a routine still running after its instruction budget, 50 million instructions, has run away and fails the call. Why that number, the project's reason: far more than a routine of the game needs, so only a runaway reaches it; measured: the original's unpacker on the largest packed file, `world.shp` (67,264 bytes out), takes 189,359 instructions, `hellcat.shp` 143,473; the whole suite runs within the budget. Source: `tools/oracle.py` (`RETURN_TRAP = 0x0FFF00`, `emu_start(addr, RETURN_TRAP, count=max_insns)`, `max_insns=50_000_000`, "did not return ... instruction budget exhausted?"); a count with a code hook in the scratchpad at `25a19a6`.
17. An access to memory outside the 2 MB fails the call with the address and the instruction that made it. Source: `tools/oracle.py`, `_unmapped` and `call` (`RuntimeError(self.fault ...)`).
18. A4 is set to `0x02AFFE` when the routine reaches the program's variables, as the game's own code keeps it. Source: `tools/oracle.py`, `call` (`if self.a4 is not None`); `SPEC.md` 4 ("Pass `a4=0x02AFFE` when the routine touches globals"); `tests/original.py` (`A4 = 0x02AFFE`, `Oracle(a4=a4)`); chapter 3 (the small-data base).
19. A hand-written routine has no convention but its own; the test sets its registers by hand, as the routine was read: `text_width` takes the text's address in A0 and its length less one in D0. Source: `tools/oracle.py`, `call` (`regs`, "e.g. {'d0': 1, 'a0': ptr} for asm routines"); `tests/original.py`, `text_width` (`regs={'a0': string, 'd0': len(text) - 1}`); chapter 4.
20. Test buffers come from a bump allocator from `0x100000`, above the stack and the program. Source: `tools/oracle.py` (`HEAP_BASE = 0x100000`, `STACK_TOP = 0x0FF000`, `alloc`).
21. A stub is a stand-in that answers for something a routine calls but that is not under test. The first tests need three, because there is no system to give out memory, clear a picture or read a file: the allocator wrapper `mem_alloc_asm` (`0x0158EC`) hands back a fixed buffer; the game's routine that clears a picture's memory, `vport_clear_planes` (`0x01A74C`, compiled C), which calls the system's `BltClear` (`jsr -$7bea(a4) ; -> gfx_BltClear` at `0x01A78A`), returns at once and the test clears the same bytes itself, so both sides start from cleared planes; inside `font_load`, which only prepares the text tests, the ten bytes of the call of `load_file_public` become `move.l #image,d0` and two `nop`s, an instruction that hands over the font's address, already in emulated memory. The routines under test are never changed ("no routine under test is touched"). Source: `tests/original.py`, docstring and `stub_allocator`, `stub_clear_planes`, `stub_font_loader`; `re/Wings.lst` `0x01A78A`; `tests/test_oracle_m1.py` (`font_load()` before `text_width` and `text_render`); `re/notes/porting-m1.md`, "How the tests establish it"; Wikipedia, "Test stub", fetched once (Elsewhere link); the review's B4 and C14.
22. The later tests add stubs of their own by the same rule, each in the test that needs it, with its reason beside it: `stub_key_os` and `stub_copper` in `tests/original.py` (exec's `Disable` and `Enable` and graphics' `WaitTOF` around the key buffer; the copper builder and its install around the fades, which the port replaces); `stub_slots` in `tests/test_oracle_m4.py` (`shape_find`, `shape_draw`); the `rts` written over `shape_draw` in `tests/test_oracle_m6.py` and a routine in `tests/test_oracle_m5.py`; the DOS slots, `mem_alloc`'s, `printf`'s and `IoErr`'s in `tests/test_oracle_m7.py`. Source: those files at the lines `tests/original.py` `stub_key_os`, `stub_copper`; `tests/test_oracle_m4.py` 321 to 338; `tests/test_oracle_m5.py` 453; `tests/test_oracle_m6.py` 43; `tests/test_oracle_m7.py` 180 to 387; the review's A2.
23. The routines that read or write the game's variables run on a state the test writes into both sides: every variable ported from the original (not the port's own state, such as its entropy generator or its arena) is registered with its original address, which lets the harness copy a state between the emulated memory and the port with the byte order turned round, and the test compares every registered global and table the two touched. A routine can run alone whenever its inputs, the game's state among them, can be set so. Source: `SPEC.md` 7.2, last point ("Every global that is ported gets an entry in a registry (`src/globals.def` ...). The test harness uses it to copy state between oracle and port with byte-order conversion"); `tests/test_oracle_m5.py` to `m7.py`, docstrings ("every registered global and table the two touched is compared"); `SPEC.md` 7.3 (the entropy stream, the port's own); the glossary's entries Big-endian and Little-endian (chapter 3); the review's B11 and C1.

## A test, read

24. The listing `test_colour_lerp_matches_over_its_range` (`tests/test_oracle_m1.py`, in the book with the header as line 1: `Original()` line 9, `compare` 11 to 15, the slow branch 17 to 22, the sweeps 24 to 28, the seed and the random triples 30 to 32): `Original()` is one emulated machine; `compare` runs the original and the port on one step and two colours and fails with both values; the sweeps fade every colour to black and to white and black to every colour at each of the 16 steps, every fade the game runs (the docstring's "against black and white in both directions"), which exercises the carry between the components at every step; then 20,000 random triples from a fixed seed (`random.Random(11)`); with `WOF_SLOW_ORACLE=1` the whole cross product of 16 steps and 4,096 by 4,096 colours. Source: the test, lines 320 to 350, and its docstring.

Source: `tests/test_oracle_m1.py` (`random.Random(11)`, `random.Random(0x57494E47)`); the tests' failure messages (`'case %d'`); `tools/ffp_soak.py`, docstring ("from a seed given on the command line, so a run can be repeated").

What that proves and what not: the clipping, the addresses, the sizes and the masks in the programme are the original's own; how the blitter combines them is documented hardware behaviour the project modelled and did not derive from the original; the port's drawing rests on the same reading of the documentation (its per-pixel rule is argued from the minterm, the shifters and the word masks), so a mistake in that reading would be shared and pass unseen. Chapter 12 returns to the model. Source: `re/notes/porting-m1.md`, "The blit is per-pixel, and why" and "What that proves and what it does not"; `tests/test_oracle_m1.py`, `test_the_blit_writes_exactly_the_shape_box`; `tests/original.py`, `clip_set`; `SPEC.md` 8, row "Drawing"; `book/BOOK.md` 3, chapter 12. The test replays through the model too, so the prose says it leaves out the port, not the model; the review's C9.

## What verified means

38. The status `verified` (chapter 4): ported and held to the original by a test of its own; for a pure routine that test is the oracle's, due before the status is set. Source: `CLAUDE.md`, Rules ("Pure routines get an oracle test before they count as `verified`"); `SPEC.md` 7.4, step 4 ("This is mandatory for pure routines") and step 5.
39. Pure is meant broadly: the specification counts arithmetic, table lookups, decoders, collision tests and state machines over plain structures; so `object_step`, which moves an object through the game's state, is `verified` under the oracle on random states written into both sides. Source: `SPEC.md` 7.4, step 4; `re/functions.csv` (`object_step`, `verified`); `tests/test_oracle_m5.py`, `test_the_objects_step_matches_the_original`; the review's C1.
40. About a quarter of the 616 routines are verified (167 at `25a19a6`, sheet only). Source: `re/functions.csv` at `25a19a6` with `csv.DictReader` (verified 167, ported 155, partial 1, replace 47, drop 31, todo 215).
41. The status is a judgement written by hand and no tool checks it (no test and no tool but the disassembler, which carries it over, reads it); the test is the evidence (the project's reason, stated as such). Source: `SPEC.md` 7.4, last paragraph; `grep` over `tools/*.py` and `tests/*.py` (only `tools/disasm.py` reads the status column of `re/functions.csv`); the review's C10.
42. Held otherwise, `ported`, are the routines whose work is to run others in turn (`logic_tick`, `frame_update`), to draw the world from the map (`draw_world`), or to talk to the system (`map_load`), held by the comparisons of whole runs, which also hold what no test of one routine can: the order and the moment in which the game calls its routines (chapter 8). 46. A shift moves the bits of a number along; one place to the right halves it. An arithmetic shift right copies the sign bit into the top, so a negative number stays negative and is halved, rounded down; a logical shift right shifts in a zero, which suits a number without a sign and turns a negative one into a large positive one; an arithmetic shift left differs from a logical one only in setting the overflow flag when the sign changes (the glossary). Source: PRM 4, `ASL`, `ASR`, `LSL`, `LSR` **(reference)**; `tools/m68k_fix.py`, `asr_word` (`(value >> 1) | (value & 0x8000)`).
47. A memory-form shift is a shift instruction whose operand is a word in memory rather than a register; it moves one bit. Source: PRM 4, `ASL`/`ASR` and `LSL`/`LSR`, "Memory Shifts" **(reference)**; `tools/m68k_fix.py`, docstring.

Why: Unicorn 2.1.4 (its QEMU m68k translator) decides whether a memory-form shift is arithmetic or logical from bit 3 of the opcode, which in the memory form belongs to the field that says where the operand lies (the effective address's mode), instead of from the shift's type field; so `asr.w d16(An)` runs as a logical shift and `lsr.w (An)` as an arithmetic one; the register forms are right. 52. 62. The condition codes, or flags, are five bits the 68000 sets after most instructions, N (negative), Z (zero), V (overflow: too large for the width), C (carry) and X (extend, set as the carry by most arithmetic, for arithmetic over several words), kept in the low byte of the status register; a conditional branch reads them. Source: PRM 1.1 and 3.1 **(reference)**; `tools/oracle.py` (`CCR_BITS`); `SPEC.md` 7.1 ("A branch reads the flags of the last instruction that set them").
63. The flags a routine leaves at its return are part of what it gives its caller: the mathffp routines leave theirs on purpose (the glue touches no flag on the way back, so a caller can branch on them), and the program branches on them at five places, all in a number formatter the game never runs. The port keeps the flags all the same, because it copies the ROM's routines instruction by instruction and those routines read their own flags in their arithmetic (`SPAdd` reads X back with `roxr`, `SPMul` with `addx`), so the flags at the return come with them. Source: `tools/oracle.py`, the comment above `CCR_TRAMPOLINE` ("The condition codes a routine leaves are behaviour"); `re/notes/ffp.md`, "How the game reaches it" ("On the way back nothing touches the condition codes"; the five sites, none of the fifteen the game reaches), "`format_float` `0x021A40` is dead" and "The port" (the helpers "each writing exactly the condition codes that instruction writes, because `SPAdd` reads the X bit back with `roxr` and `SPMul` with `addx`"); the review's B14 and C10.
64. Unicorn, like QEMU on which it is built, works the flags out lazily: it keeps the last operation and its operands and computes the flags only when an instruction needs them, because most flags are never read. Reading the status register from outside hands back whatever was last worked out: `addq.w #1` on `0x7FFF` reports N without V, where a 68000 sets both; `tst.w` on `0x00010000`, whose lower word is zero, reports nothing, where a 68000 sets Z. Source: Bellard, *QEMU, a Fast and Portable Dynamic Translator*, USENIX 2005, section 3.3 "Condition code optimizations" (lazy evaluation: "instead of computing the condition codes after each x86 instruction, it just stores one operand, the result and the type of operation"; "a critical point to get good performances"; described there for the x86 target) **(reference)**; `tools/oracle.py`, the comment above `CCR_TRAMPOLINE`; `re/notes/headless.md`, "Unicorn, as it behaves here"; `SPEC.md` 4, "The oracle"; `tests/test_oracle_ffp.py`, `CONTROL` (the expected flags); the review's C10 and C12.
65. The oracle's answer: with `ccr=True` the routine returns through two instructions of the oracle's own, a move from the status register into a memory slot and a jump to the trap address, neither of which changes a flag; the move runs inside the emulation and forces the flags to be worked out. Source: `tools/oracle.py` (`CCR_TRAMPOLINE = struct.pack('>HLHL', 0x40F9, CCR_SLOT, 0x4EF9, RETURN_TRAP)`, the comment); PRM 6, `MOVE from SR`, and 4, `JMP`: condition codes not affected **(reference)**. The PRM lists `MOVE from SR` in section 6 among the privileged instructions because it is privileged from the 68010 on; on the 68000 it is not (an MC68000 entry in section 4 could not be checked against the online copy); the oracle runs the routine in supervisor mode anyway (`call` writes `SR` `0x2000`); the prose says only that the move changes no flag. The review's B21.

Source: `tests/test_oracle_ffp.py`, the comment above `CONTROL` ("every one of them but the last would come out wrong") and `test_the_oracle_reports_the_68000s_condition_codes` (nine parametrised cases).
