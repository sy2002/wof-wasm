# Fact sheet: chapter 20, The original's quirks

Every claim the chapter makes, one line each, with its source, in the order of the chapter. A claim without a source goes to the list at the end and stays out of the draft. A general fact that the notes do not state is sourced in a reference work and marked **(reference)**; what the game does always comes from the notes, the listing and the port's sources. No "How we know" box and no "What went wrong" box (`book/BOOK.md` 4, point 6): where something was checked, one plain sentence names the instrument's chapter. A quirk is told as what the code does, never as a mistake of the programmers unless the listing shows the mistake, and no design reason is claimed.

Counts are of the branch's base, `6d9492c`, counted in the files named, by reading or with the command in the counts table at the end. Run for a fact, each on one core: one run of the native library (`tests/libwofcore.dylib`, not rebuilt) through `book/tools/figures.py`'s `run_core` and `table_reader`, the island run of chapter 13 with a dive onto map a's island appended (under a second), sampling the player's record and the fifteen object records every second VBlank from 3530 to 3700, for the wreck's explosions and figure (c); `tools/headless_os.py`'s `adf_order` and `name_hash` on `original/wof.adf`, for the directory's chains. No test run, no headless original, no browser, no rebuild.

Words used in the sheet as the chapter will use them. A **quirk** is a place where the original's code does something odd: it reads past a table, hands a routine the wrong thing, keeps code nothing runs, or disagrees with its manual; the word needs no glossary entry. The four **kinds** are the chapter's sorting: (1) accidents that reach the game, (2) code nothing calls and values nothing reads, (3) what a real Amiga does that neither the headless original nor the port reproduces, (4) the port's deliberate divergences. A **deliberate divergence** is the port's change of the original made on purpose by the owner's decision (a term of this chapter, claim 92); a **mistake** is the port's, found and put right (chapter 9). The **map list** is the list of map records `map_load` allocates (chapter 13's record list), and **the map list's address** where the allocator put it, `map_list_address` (`0x024628`) in the port. An **explosion record** is an object record of kind 8 that `object_spawn` makes (chapter 15). A **chain** is a directory's hash chain (claim 27); an **entry** is the directory's, what `ExNext` hands out (chapter 19's word). **The harness** and **the headless original** are chapter 6's; **a real Amiga** is the machine; **the release build** is `dist/core.wasm`. "Dead" is the notes' word; the chapter says "nothing calls", "nothing reads", "nothing reaches", and "never holds".

The reference works:

- *Amiga ROM Kernel Reference Manual: Exec* (Addison-Wesley, 1990, for Release 1.3), the chapter "Memory Allocation": `AllocMem` hands out a block from the system's free memory lists, so the address depends on the machine's memory and on what was allocated before; `https://archive.org/details/amiga-rom-kernel-reference-manual-exec`, already the Elsewhere line of Interrupt and VBlank server. **(reference)**
- *The AmigaDOS Manual*, 3rd edition (Bantam, 1991), the chapters on the file system: a directory's header block holds a hash table of 72 longs on a 512-byte block, an entry goes into the chain its name's hash names, `ExNext` walks the table in order and each chain from its head. Chapter 3 told the 72 chains; chapter 19 linked them. **(reference)**
- *Amiga Hardware Reference Manual*, 3rd edition (Addison-Wesley, 1991), appendix F, the 8520 CIA: at reset the timers' latches hold all ones; chapter 6 ("Display"), a PAL frame of 313 lines of 227 colour clocks. Chapter 18 cites it. **(reference)**
- Wikipedia, "Amiga Old File System", `https://en.wikipedia.org/wiki/Amiga_Old_File_System`, fetched once: AmigaDOS hashes a name to pick the long of the directory block that heads a bucket list, 72 entries on a 512-byte block; for the Elsewhere line of Hash chain. **(reference)**

## 2. An address for an x

8. While a crashed aircraft lies on the ground and slides to a stop, the crash routine `crash` (`0x01AFBA`) leaves an explosion every tick by a call of `object_spawn` at `0x01B304`; on land it also hits the record under the wreck and the soldiers within 8. Source: `re/notes/porting-m5.md`, "The wreck's explosion and the map list's address" (its "While the wreck rests" covers the slide: see "Where a source was wrong or silent"); `re/Wings.lst` `0x01B2A2`–`0x01B33C` (the airspeed down by `0x55` a tick, then the call; `crash_hit` and `soldiers_hit_c` with 8 when on land); `src/player.c` (the `rest` branch, comment at `0x01B304`); the scratch run (claim 15): explosion records at x 12,280 while the record's state is 4 and its height 2, none after state 8.
9. `object_spawn` (`0x010820`) makes an explosion for a map record: it takes the record's address, a height and a flag; the explosion's x is the record's byte offset from the map list's start, times four, as a word (a record of two bytes for eight pixels), at 12 pixels above the height given. Source: `re/Wings.lst` `0x010820`–`0x010852` (`move.l $4(a7),d1`, `sub.l -$69d6(a4),d1`, the list's start `map_records`, `lsl.w #$2,d1`, `move.w d1,(a0)`, `moveq #$c,d1`, `add.w $8(a7),d1`); `src/objects.c`, `wof_object_spawn` (comment: "at the record's world x (its byte offset times four, a word), 0x0C above y"); `book/docs/part-2/world.md` (one record every eight pixels).
10. Every other call hands it a map record's address: `wreck_smoke` at `0x01AF72` and `ground_contact` at `0x01BBE8` the result of `record_at`, the crash's own calls at `0x01B0CE`, `0x01B166` and `0x01B3C4` the record under the aircraft kept in a local, each with a height and a long of 0, ten bytes. Source: `re/Wings.lst` at those addresses (`jsr record_at`, `move.l d0,-(a7)`; `move.l -$6(a5),-(a7)`; `clr.l -(a7)`; `lea.l $a(a7),a7`).
11. The call at `0x01B304` pushes a long of 0, the aircraft's height word, then its x word, eight bytes: so the long `object_spawn` reads where the address belongs is the x and the height side by side, x in the upper word, and the height and the flag it reads are both 0. Source: `re/Wings.lst` `0x01B304`–`0x01B318` (`clr.l -(a7)`, `move.w (a0),-(a7)`, `move.w $2(a0),-(a7)`, `addq.w #$8,a7`); `re/notes/porting-m5.md` (ibid.: "passes the aircraft's x and y words where `object_spawn` wants the map pointer, and nothing where it wants the height"); the player's record: `+0x00` the height, `+0x02` the x (`src/records.def`, `player`).
12. So the explosion's x is the long less the map list's address, its low word times four; the height 12. Source: claims 9 and 11; `re/notes/porting-m5.md` ("the record is at the x of the long `(x << 16 | y)` less the map list's address (as a word, times four) and at height `0x0C`").
13. *(Derived from the listing.)* Only low words take part: the low word of a 32-bit subtraction depends only on the low words of the two numbers, and `lsl.w` and `move.w` use only the low word, so the explosion's x is four times the height less the address's low word, kept to 16 bits; the aircraft's x drops out. Source: `re/Wings.lst` `0x010824`–`0x01084A`; arithmetic.

## 3. The order of the directory

28. The load and save dialog lists the game's directory in the order dos.library's `ExNext` hands out its entries, without sorting (chapter 19). Source: `re/notes/frontend.md`, "Load and save dialog" (The file list); `book/docs/part-2/front-end.md`.
29. **Hash chain**, a term of this chapter: one of the 72 lists into which the file system sorts a directory's entries, the list chosen for each entry by a number worked out from its name. Source: `re/notes/frontend.md`, "The order of the file list"; `tools/headless_os.py` (`HASH_SIZE = BLOCK // 4 - 56`, "72 chains per directory"); *The AmigaDOS Manual* **(reference)**.
30. Why chains: a file is found by reading one chain instead of every entry (chapter 3). Source: `book/docs/part-1/disk.md`. Linked.
31. The hash: start with the name's length; for each character, times 13 plus the character in upper case, kept to 11 bits (`& 0x7FF`); the chain is that modulo 72. Upper case is plain ASCII, since an old file system disk is not international. Source: `re/notes/frontend.md` (the formula); `tools/headless_os.py`, `name_hash`; `src/fs.c`, `name_hash`.
32. 72 is a 512-byte block's 128 longs less the 56 the block's other fields take. Source: `tools/headless_os.py` (`BLOCK // 4 - 56`); Wikipedia, "Amiga Old File System" ("BSIZE/4-56 ... 72 entries with the usual 512 byte blocks") **(reference)**. Sheet only, or a clause.
33. `ExNext` walks chain 0 upward, and inside a chain from its head: the order is the chains', not the alphabet. Source: `re/notes/frontend.md` (ibid.); *The AmigaDOS Manual* **(reference)**.
34. The game's directory on the disk, 14 entries in 13 chains, in that order: `Wings` 1, `wingt` 2, `.info` 7, `shapes` 22, `wofsongs` 26, `wings.info` 32, `maps` 33, `sounds` 42, `UFXintro` 43, `highscore` 49, `songplay` 53, `newarmyfont` 53, `rank.iff.info` 58, `wof.mission 3` 64. Source: `re/notes/frontend.md` (the list); `tests/test_frontend.py`, `test_the_disk_image_gives_the_order_the_file_system_hands_out` (the names); the chains by `name_hash` and `adf_order` (counts table).
35. Every entry of the disk's five directories, the disk's top, the game's, `shapes`, `maps` and `sounds`, lies in the chain the hash gives; the test asserts it for the game's directory and `shapes`. Source: `re/notes/frontend.md` ("Every entry of five directory blocks ... has the chain that hash gives"); the test (claim 34); `adf_order` over the five (counts table).
36. The order follows from the names alone: the dialog shows only names that begin `wof.`, their chains come from the hash, and the disk's one such file, `wof.mission 3`, is older than anything the player saves. Source: `re/notes/frontend.md`, "For the port", point 1.
37. Unconfirmed, as chapters 1 and 3 said: that a real Kickstart 1.3 `ExNext` walks the chains in this order at all, and that a new entry goes to the head of its chain rather than the tail; both are documented, neither was checked on a machine, and the owner decided not to check it on the Amiga. Source: `re/notes/frontend.md`, "Unobserved"; `SPEC.md` 6.2, Storage ("the owner decided ... not to check it on the Amiga"); `book/docs/part-1/faithful.md`; `book/docs/part-1/disk.md`.
38. The disk cannot settle head or tail: thirteen of its chains hold two or three entries, and in every one the head has the earlier date, which reads as insertion at the tail; but most of the game's files carry the date 0 a copier writes when it keeps no dates, so the entries that look oldest may have been written last, and then the disk reads as insertion at the head. Source: `re/notes/frontend.md`, "Unobserved".
39. Head or tail matters only when two saved games share a chain: a game saved as `wof.flight 4` falls in chain 64 with `wof.mission 3`, so at the head it is listed first and at the tail second; two names in chains of their own, as the tests' `wof.amission 3` in 34, come in chain order either way. Source: `re/notes/frontend.md` (point 3; "the two saved games ... fall in chains 34 and 64"); `name_hash('wof.flight 4')` = 64 (counts table).
40. The harness puts a saved file at the head of its chain, where a real file system puts a new entry; the port does the same: what the game writes goes into the file system's overlay in front of the read-only disk, and inside a chain a written file comes before the disk's, two written files newest first. Source: `re/notes/frontend.md` ("puts a file a run has saved at the head of its own chain"); `re/notes/porting-m3.md`, "The file system's write side" and "The order of the list"; `src/fs.c`, the comment above `name_hash` and `wof_fs_dir_entry`.
41. The shell stores the overlay in the order it wrote it and puts it back in that order, because the order is part of what the list is made of. Source: `re/notes/porting-m3.md`, "The file system's write side"; `SPEC.md` 6.2, Storage.
42. Held: the port's chains against the harness's hash (`tests/test_front_port.py`, `test_the_directory_comes_out_in_the_file_systems_own_order`), two names in one chain newest first (`test_two_names_in_one_chain_come_newest_first`), and the harness's hash against the disk (claim 35). Source: the tests; `re/notes/porting-m3.md`, "The order of the list".
43. A saved game keeps the case the player typed on the machine; the harness keeps lower case (chapter 6). Source: `re/notes/frontend.md`, point 2; `book/docs/part-1/headless.md`. Sheet only.
44. Listing: `name_hash` (c, `src/fs.c`, with the comment above it). Shown nowhere before; chapter 19 showed `wof_fs_dir_entry`.
45. Listing: `test_the_disk_image_gives_the_order_the_file_system_hands_out` (py, `tests/test_frontend.py`).

Figure (b), new, hand-drawn, `directory-chains.svg`: the 72 chains as a grid of six columns and twelve rows, read row by row; the 14 entries in their 13 chains, numbered 1 to 15 in the walk's order with `wof.flight 4` at the head of chain 64 as 14 and `wof.mission 3` as 15; the names the dialog lists marked; chain 64 marked "head, or tail? unconfirmed".
