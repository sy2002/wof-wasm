# Randomness and video rate

Answers points 8 and 9 of `SPEC.md` section 10. Addresses use the standard load layout.

## The generator

The game has one random source in use: `rand_beam` (`0x0203BE`), called from 43 sites.

```c
uint16_t rand_beam(void)
{
    int32_t v = (int16_t)rand_seed_const * 0x1AFB + 0x1FCCD;   /* muls.w, then add.l */
    rand_state = (uint16_t)v ^ VHPOSR;                         /* eor.w with 0xDFF006 */
    return rand_state;
}
```

- `rand_seed_const` (`0x026912`) is written **only** by `rand_set_seed` (`0x0203DA`), which stores its argument into both `rand_state` (`0x026910`) and `rand_seed_const`. Between seedings it never changes.
- `rand_beam` reads `rand_seed_const` but writes `rand_state`. Its result is therefore a constant exclusive-ored with the raster beam position at the moment of the call. **All variation comes from the beam position**, that is, from how much CPU time has passed since the last VBlank.
- `rand_lcg_unused` (`0x0203AA`) is a conventional generator on `rand_state` with the same multiplier and increment. Nothing calls it.
- `read_vhposr` (`0x015D5A`) returns the raw beam position. The front end (`0x018262`, `0x01F41A`) uses it, the former together with `rand_set_seed`.

VHPOSR holds the low 8 bits of the vertical beam position in its high byte and the horizontal position, in units of two low-resolution pixels (0 to `0xE3`), in its low byte.

## Consequences

The original is **not** a pure function of seed and input bytes. Its behaviour also depends on cycle-exact timing through the beam position. A port cannot reproduce that timing, and does not need to.

- The core takes randomness from an **entropy stream**: an explicit sequence of 16-bit beam-position values, one consumed per `rand_beam` call. The stream is generated by a small deterministic generator inside the core, seeded by `wof_init`, producing values with the shape of a real VHPOSR (high byte uniform over 0 to 255, low byte uniform over 0 to `0xE3`).
- With the stream fixed, the port is deterministic: replays, save states and tests work.
- **The headless original (milestone M2) must hook reads of `0xDFF006` and serve the same stream.** Then original and port consume identical values as long as the port calls `rand_beam` in exactly the original order. A divergence in call order shows up immediately as a state mismatch, which makes this an additional fidelity check rather than a nuisance.
- Statistical behaviour matches the original: in both, each call sees an effectively independent beam position.

## Video rate

The program never reads `VBlankFrequency` or `PowerSupplyFrequency` from ExecBase, nor `DisplayFlags` from GfxBase. It does not distinguish 50 Hz from 60 Hz machines. On a PAL machine everything simply runs at 50/4 ticks per second instead of 60/4. The port's 50 Hz option is therefore nothing more than a different VBlank clock rate.
