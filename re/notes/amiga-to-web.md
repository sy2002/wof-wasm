# Amiga to Web: the idea of a template

An idea of the owner's, 2026-10-01, written down before it is started: what was done for Wings of Fury could be the start of a reusable way of preserving Amiga games as faithful browser ports. This note says what of this repository is reusable as it stands, what is the work of each game, which games the method reaches and which it does not, what "start" can mean, and the shape such a template could take. It is a plan for a possible future project, not a description of anything that exists.

## The idea

A GitHub template repository, "Amiga to Web": one clones it, names it after the game, places the Kickstart ROM and the disk image, opens the sessions the handbook names, and says "start". Out comes, after days of clock time and a large budget of tokens, a faithful port of the kind this repository holds, with its notes, its tests and its proof.

## What this repository already holds that is game-independent

Three layers, none of which knows the game:

1. **The instruments** (`tools/`): the hunk loader and the disassembler driven by a names file (`disasm.py`, `hunk.py`, `m68kdis.py`), the control-flow skeleton (`skel.py`), the 68000 oracle under Unicorn with the fix for Unicorn's memory-form shift (`oracle.py`, `m68k_fix.py`), the headless original with its stubs of exec, DOS, graphics and intuition, its memory served by a bump allocator, its files served from the extracted disk, the beam position as the one source of chance, VBlanks only where the program waits, the dumps, the write summaries and the observers by routine name (`headless.py`, `headless_os.py`, `headless_dump.py`, `headless_writes.py`), the Paula model (`headless_paula.py`), the ROM check (`rom.py`), the table extraction by a manifest (`extract_tables.py`), the reach map (`reach_observe.py`), the Markdown check and the run comparison. Two tools are this game's: the shape container and packer decoders (`ppkc.py`, `rpck.py`), which other titles from the same developer may share.
2. **The runtime** (`src/` without the game's logic): the arena that hands out zeroed memory (`mem.c`), the virtual file system with AmigaDOS's directory order (`fs.c`), the coroutines that let blocking code wait (`coro.h`), the entropy stream (`rand.c`), the Paula model as the mixer (`audio.c`), the framebuffer with a palette per row (`video.c`), the ILBM reader (`iff.c`), the topaz font (`font.c`), the bit-exact `mathffp` (`ffp.c`), the trace for the tests (`trace.c`), the key conversion table from the ROM. Together they are an Amiga for one program, without the Amiga.
3. **The shell and the test harness** (`web/`, the generic half of `tests/`): the clock at the VBlank rate, the WebGL picture in the Amiga's pixel aspect with the 2D fallback, the audio worklet, the raw Amiga key codes, the storage, the help screen, the pause sign, fullscreen; the Chrome and Firefox drivers, the pixel-exact screenshot checks under a true scale factor, the two-phase suite, the fixtures that give every test a fresh core.

And the layer that weighs nothing and matters most, **the method and its rules**: `CLAUDE.md`, `CONTROLLER.md` with the arrangement of one controller and its workers, the review discipline and the pitfalls, the shape of `SPEC.md` (the definition of faithful in three parts, the porting rules of section 7, the verification table of section 8, the milestones with their gates), and the porting method of M4 to M7: the reach map that decides what is ported by what the scripts execute, the marked stand-ins that fail every comparison reaching them, the open and the closed loop, the completeness list, the controls that break the port on purpose, the autopilots that find a landing or an attack. Every mistake made once in this project is written down with the instrument that caught it; the next game starts without them.

## What is the work of each game

The names, the notes, the tables manifest, every ported routine of the game's logic, the data formats and their decoders, the mission scripts and the autopilots, the keys decision, and the owner's tests and decisions. Of the twelve days of this project, about two fifths went into the three layers and the method, three fifths into the game. A template takes away the two fifths and the mistakes; the three fifths stay, and they are reading, porting and proving.

## Which games the method reaches

The method rests on how this game is built: compiled C (Manx Aztec, 16-bit `int`), one executable that is not packed, files through AmigaDOS, memory through exec, the blitter driven from a few routines, no hardware sprites, the copper used for palettes per row and little else, a separate music player as a program of its own. For a game of this construction the headless original is the instrument that makes everything else possible, because the game's own code runs under it from `main` with the operating system stubbed.

Many Amiga games are built the other way: hand-written assembly throughout, a trackloader instead of a file system, self-modifying code, hardware sprites, dual playfields, copper tricks, overlays, a packed executable with the loader in the way. For those the OS stubs serve nothing, and the oracle would have to become a chip-level emulator running beside the port, a different and larger instrument, with the reach map and the loops built on its cycle-exact state instead of the program's waits. The honest scope of the template is therefore games written in C or in disciplined assembly on top of AmigaOS: a real class (much of Broderbund's and Cinemaware's catalogue, many conversions from the PC and the ST), not any disk image.

## What "start" can mean

Not a button. The controller needs the owner at three points that no session replaces: the decisions (the keys, which of the original's quirks to keep, what to measure on a real machine), the look and the listen (the fades, the colours, the sound), and the budget. It needs the game to be understood before the milestones can be cut, which is the reading of M2 and of the points before M4. What a template makes true is narrower and still worth a lot: a controller told "start" can run M0 to M2 by itself (the build, the first picture, the headless original reaching a mission), write the first findings into the notes, and come back with the plan and the questions, as the handbook already says a controller should.

## The shape it could take

- **Derive it from this repository, not from a design.** Move the three layers into a template repository: `tools/` and the generic `src/` and `web/` and `tests/` as they are, `original/` empty but for the README's instructions on the ROM and the disk image, a `game/` directory for the per-game sources, `SPEC.md` as a skeleton whose sections 1 to 8 stay and whose section 3 and the milestones are placeholders, `CLAUDE.md` and `CONTROLLER.md` with the game's name taken out, and a `METHOD.md` that says in order what the milestones are, what each one's gate is, and which instrument answers which question. The per-game and the generic halves of this repository are not separated today (the game's logic and the runtime share `src/`, the scripts and the drivers share `tests/`); separating them is the first task of the template, and it tells what is really generic.
- **Keep this repository as the worked example** the template points to, and the book about it as the template's manual: its first and third parts describe exactly the method and the tools.
- **Prove it on a second game before calling it a tool.** A template is proven only when a second game goes through it. Choose one of the same construction, run the whole method, and let that project's chronicle say what the template lacked; that is the honest first milestone of "Amiga to Web", and the best material for a last chapter of the book.
- **Do it after the release and the book**, when both are done and nothing of this project is in flight.
